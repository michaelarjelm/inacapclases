Bloque 01

La base de los
Mundiales

Una colección partidos con un documento por cada partido de la historia de los Mundiales (1930–2022). Cada documento mezcla campos planos, subdocumentos y arreglos.

Concepto

mundiales_db — Estructura

Anatomía de
un partido

Cada documento de la colección partidos tiene tres tipos de campo, y hoy trabajaremos con los tres:

  • Campos planos: mundial, fase, fecha, resultado, penales.
  • Subdocumentos (objetos): sede, local, visitante, marcador_penales.
  • Arreglos: etiquetas (lista de textos), goleadores y tarjetas (listas de subdocumentos).
📦
Esto es modelado documental

En una BD relacional, goleadores y tarjetas serían tablas aparte unidas por claves. En MongoDB viven dentro del mismo documento del partido.

Comando

mundiales_db — Cargar y explorar

load + findOne

MongoDB Shell 
// 1. Cargar el dataset (crea la colección partidos)
load("partidos_mundiales_insertMany.js")

// 2. Seleccionar la base de datos
use mundiales_db

// 2. Cuantos partidos hay en total
db.partidos.countDocuments({})

// 3. Ver la forma de un documento
db.partidos.findOne({ "mundial": 2010, "fase": "Final" })

Antes de consultar, siempre conviene mirar un documento completo con findOne() para conocer los nombres exactos de los campos anidados.

Bloque 02

Sub
documentos

Un documento puede contener otros documentos adentro. Es la forma natural de agrupar datos que pertenecen juntos.

Concepto

Subdocumentos — Qué son

Documentos
embebidos

Un subdocumento (o documento embebido) es un objeto que vive como valor de un campo dentro de otro documento. En nuestra base, sede no es un texto: es un objeto con sus propios campos estadio, ciudad y pais.

Agrupar así tiene sentido cuando esos datos siempre se consultan juntos y pertenecen a una sola entidad. El estadio, la ciudad y el país de un partido son inseparables del partido.

🧱
Idea clave

Los subdocumentos pueden anidarse en varios niveles. Un partido tiene marcador_penales, que a su vez tiene local y visitante.

Concepto

Subdocumentos — Decisión de modelado

Embeber o
referenciar

La gran decisión al modelar en MongoDB: ¿guardo los datos relacionados adentro (embebido) o en otra colección (referenciado)?

Embebido (lo de hoy)
{ sede: { ciudad, pais } }

Todo en un documento. Se lee de una sola vez, rápido. Ideal cuando los datos se consultan juntos y pertenecen a la misma entidad.

Referenciado
{ sede_id: ObjectId("...") }

Guarda un identificador a otra colección. Evita repetir datos compartidos, pero requiere cruzar colecciones (lo veremos con $lookup).

💡
Regla práctica

Si los datos "viven y mueren" con el documento padre, se embeben. Si se comparten entre muchos documentos, se referencian.

Bloque 03

Dot
notation

Para consultar un campo que está dentro de un subdocumento usamos la notación de punto: "padre.hijo".

Concepto

Dot notation — Cómo funciona

La notación
de punto

Para llegar a un campo anidado, escribimos la ruta completa entre comillas, separando cada nivel con un punto: "sede.pais", "local.goles", "marcador_penales.local".

Las comillas son obligatorias cuando el nombre del campo lleva un punto: sin ellas, JavaScript no lo interpreta como una clave válida.

⚠
El error más común

Escribir { sede: { pais: "Brasil" } } NO busca por país: busca un sede que sea exactamente ese objeto completo y nada más. Lo veremos en la siguiente lámina.

Comando

Dot notation — Consultas

find en campos anidados

MongoDB Shell 
// Partidos jugados en Brasil (campo dentro de sede)
db.partidos.find({ "sede.pais": "Brasil" })

// Partidos donde la selección local fue Chile
db.partidos.find({ "local.seleccion": "Chile" })

// Partidos donde el local marcó 5 o más goles (goleada de local)
db.partidos.find({ "local.goles": { $gte: 5 } })

// Niveles anidados: ganador de tanda de penales con 4+ (campo dentro de marcador_penales)
db.partidos.find({ "marcador_penales.local": { $gte: 4 } })

// Dot notation + proyección: solo selecciones, sin _id
db.partidos.find(
  { "sede.pais": "Chile" },
  { "local.seleccion": 1, "visitante.seleccion": 1, "fase": 1, "_id": 0 }
)

La ruta entre comillas vale tanto en el filtro como en la proyección. Los operadores ($gte, $lt, etc.) funcionan igual sobre campos anidados.

Comando

Dot notation — El error a evitar

objeto completo vs. punto

MongoDB Shell 
// INCORRECTO: busca un sede que sea EXACTAMENTE este objeto,
// con esos campos, en ese orden y sin ninguno mas. Casi nunca coincide.
db.partidos.find({ "sede": { "pais": "Brasil" } })
// -> 0 resultados (sede tambien tiene estadio y ciudad)

// CORRECTO: busca solo por el campo pais dentro de sede
db.partidos.find({ "sede.pais": "Brasil" })
// -> todos los partidos jugados en Brasil

Pasar un objeto como valor exige una coincidencia exacta y total. La notación de punto consulta un campo interno sin importar el resto del subdocumento. Esta es la confusión número uno al empezar con subdocumentos.

Bloque 04

Arreglos

Un campo puede contener una lista de valores. En MongoDB hay dos tipos que usaremos: arreglos simples y arreglos de subdocumentos.

Concepto

Arreglos — Dos tipos

Simples vs.
de subdocumentos

Nuestros partidos tienen los dos tipos de arreglo, y se consultan de forma distinta:

Arreglo simple
etiquetas: [ "goleada", "con_roja" ]

Una lista de valores sueltos (textos o números). Se pregunta directo: "contiene este valor".

Arreglo de subdocumentos
goleadores: [ { jugador, minuto }, ... ]

Una lista de objetos, cada uno con sus campos. Se consulta con dot notation y, para varias condiciones, con $elemMatch.

📋
En la colección partidos

Simple: etiquetas. De subdocumentos: goleadores y tarjetas.

Bloque 05

Consultar
arreglos

Desde la coincidencia más simple hasta $elemMatch, el operador que resuelve el problema de las condiciones múltiples.

Concepto

Arreglos — Coincidencia directa

¿Contiene
el valor?

Para un arreglo, preguntar { campo: valor } significa "el arreglo contiene ese valor" (no que sea igual al arreglo completo).

Lo mismo aplica con dot notation a un arreglo de subdocumentos: { "goleadores.seleccion": "Argentina" } devuelve los partidos donde algún goleador es de Argentina.

✅
Cómodo

MongoDB recorre el arreglo por ti. No necesitas índices ni bucles: si algún elemento coincide, el documento aparece.

Comando

Arreglos — Coincidencia directa

find dentro de un arreglo

MongoDB Shell 
// Arreglo simple: partidos etiquetados como "goleada"
db.partidos.find({ "etiquetas": "goleada" })

// Arreglo de subdocs: partidos con algún goleador argentino
db.partidos.find({ "goleadores.seleccion": "Argentina" })

// Partidos con alguna tarjeta roja
db.partidos.find({ "tarjetas.tipo": "roja" })

// Partidos con algún gol después del minuto 90 (en el alargue)
db.partidos.find({ "goleadores.minuto": { $gt: 90 } })

En todos los casos, basta con que un elemento del arreglo cumpla la condición para que el documento aparezca en el resultado.

Concepto

Arreglos — El problema

Condiciones que
se cruzan

¿Y si quiero partidos con un goleador argentino que además haya marcado de penal? La tentación es poner dos condiciones con dot notation:

⚠
Falso positivo

{ "goleadores.seleccion": "Argentina", "goleadores.de_penal": true } devuelve partidos donde un goleador es argentino y otro distinto marcó de penal. ¡No es lo que pedimos!

MongoDB evalúa cada condición contra todo el arreglo por separado. Para exigir que un mismo elemento cumpla todo, existe $elemMatch.

Comando

Arreglos — $elemMatch

$elemMatch el mismo elemento

MongoDB Shell 
// MAL: condiciones sueltas, las puede cumplir goleadores distintos
db.partidos.find({
  "goleadores.seleccion": "Argentina",
  "goleadores.de_penal": true
})

// BIEN: un MISMO goleador argentino que marcó de penal
db.partidos.find({
  "goleadores": { $elemMatch: { "seleccion": "Argentina", "de_penal": true } }
})

// aquí: un gol marcado después del minuto 90 que no haya sido de penal
db.partidos.find({
  "goleadores": { $elemMatch: { "minuto": { $gt: 90 }, "de_penal": false } }
})

$elemMatch agrupa varias condiciones y exige que un solo elemento del arreglo las cumpla todas a la vez. Es imprescindible en arreglos de subdocumentos.

Concepto

Arreglos — Más operadores

$size y $all

Dos operadores más para consultar arreglos:

$elemMatch
un elemento cumple varias condiciones
goleadores: { $elemMatch: {...} }
$size
el arreglo tiene N elementos
goleadores: { $size: 0 }
$all
contiene TODOS estos valores
etiquetas: { $all: ["goleada","con_roja"] }
Comando

Arreglos — $size y $all

find con $size y $all

MongoDB Shell 
// Partidos sin goles: el arreglo goleadores esta vacio (0-0)
db.partidos.find({ "goleadores": { $size: 0 } })

// Partidos que son goleada Y tuvieron tarjeta roja (ambas etiquetas)
db.partidos.find({ "etiquetas": { $all: [ "goleada", "con_roja" ] } })

// Combinado: finales con muchos goles que se fueron a penales
db.partidos.find({
  "fase": "Final",
  "etiquetas": { $all: [ "muchos_goles", "con_penales" ] }
})

$size compara la cantidad exacta de elementos. $all exige que el arreglo contenga todos los valores listados (en cualquier orden).

Bloque 06

Modificar
arreglos

Agregar, quitar y evitar duplicados dentro de un arreglo, sin reemplazar el documento completo.

Concepto

Modificar — Operadores

$push, $pull
y compañía

Estos operadores van dentro de un updateOne / updateMany, igual que $set:

$push
agrega un elemento al arreglo
{ $push: { etiquetas: "clasico" } }
$pull
quita los que cumplan la condición
{ $pull: { etiquetas: "clasico" } }
$addToSet
agrega solo si no existe (sin duplicar)
{ $addToSet: { etiquetas: "goleada" } }
$pop
quita el primero (-1) o el último (1)
{ $pop: { goleadores: 1 } }
$each
agrega varios de una vez (con $push)
{ $push: { etiquetas: { $each: [...] } } }
Comando

Modificar — Arreglo simple

$push y $pull en etiquetas

MongoDB Shell 
// Agregar la etiqueta "clasico" a la final del 2022
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $push: { "etiquetas": "clasico" } }
)

// Quitar esa etiqueta (deshacer)
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $pull: { "etiquetas": "clasico" } }
)

// $addToSet: no la duplica si ya existe
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $addToSet: { "etiquetas": "muchos_goles" } }
)

Diferencia clave: $push agrega siempre (puede duplicar); $addToSet agrega solo si el valor no estaba en el arreglo.

Comando

Modificar — Arreglo de subdocumentos

$push y $pull en goleadores

MongoDB Shell 
// Agregar un goleador (un subdocumento completo) a un partido
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $push: { "goleadores": {
      "jugador": "Jugador Prueba", "seleccion": "Argentina",
      "minuto": 90, "de_penal": false, "autogol": false
  } } }
)

// Quitar ese goleador de prueba por su nombre
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $pull: { "goleadores": { "jugador": "Jugador Prueba" } } }
)

// Quitar TODAS las tarjetas amarillas de un partido (condicion dentro de $pull)
db.partidos.updateOne(
  { "mundial": 2022, "fase": "Final" },
  { $pull: { "tarjetas": { "tipo": "amarilla" } } }
)

En arreglos de subdocumentos, $push recibe el objeto completo y $pull recibe una condición: elimina todos los elementos que la cumplan.
