01 — SSH
Bloque 01 · Criterio 3.1.2
Conexión
por SSH

Windows Server se administra por RDP (escritorio gráfico). Linux Server se administra por SSH: una consola de texto remota, cifrada y liviana. Todo lo de hoy se hace escribiendo comandos.

Concepto
01 — SSH · La llave privada en Windows
Proteger la llave
(.pem) en Windows

Al crear la instancia descargaste un archivo .pem (la llave privada, normalmente vockey.pem). Esa llave es como tu contraseña: SSH exige que solo tu usuario pueda leerla. Si Windows la deja accesible a otros usuarios, la conexión se rechaza por seguridad.

Importante: en Windows los permisos no se cambian con chmod (ese comando es de Linux/Mac). En Windows se usa icacls, que es el equivalente para gestionar permisos de archivos.

💡
Paso previo: abrir PowerShell en la carpeta de la llave

Guarda vockey.pem en una carpeta fácil de ubicar, por ejemplo Descargas. Abre esa carpeta en el Explorador de archivos, manten presionada la tecla Shift, haz clic derecho sobre un espacio vacío y elige "Abrir la ventana de PowerShell aquí" (en Windows 11 puede decir "Abrir en Terminal"). Así los comandos actúan sobre la llave sin tener que escribir la ruta completa.

Pasos
01 — SSH · Proteger la llave con icacls
Los tres comandos
icacls
Windows PowerShell — tu equipo local
# 1. Reiniciar los permisos del archivo a los valores heredados de fabrica PS> icacls.exe vockey.pem /reset # 2. Dar permiso de solo lectura (R) UNICAMENTE a tu usuario de Windows # $env:USERNAME se reemplaza solo por tu nombre de usuario PS> icacls.exe vockey.pem /grant:r "$($env:USERNAME):(R)" # 3. Quitar la herencia: elimina al resto de usuarios del archivo PS> icacls.exe vockey.pem /inheritance:r Successfully processed 1 files. # respuesta esperada en cada paso
⚠
Si te saltas este paso...

Al conectarte verás el error Permissions for 'vockey.pem' are too open ... This private key will be ignored y SSH no te dejará entrar. Ejecuta los 3 comandos de arriba y reintenta.

✓
¿Practicas en casa con Mac o Linux?

Ahí sí aplica chmod: con un solo comando, chmod 400 vockey.pem, la llave queda como solo-lectura para tu usuario. En Windows usa siempre los icacls de arriba.

Concepto + Pasos
01 — SSH · Conectarse por SSH
Entrar al servidor
por SSH

SSH (Secure Shell) abre una sesión de terminal remota y cifrada contra el servidor. Con la llave ya protegida, para conectarte necesitas dos datos: la IP pública de tu instancia y el usuario por defecto de RHEL, ec2-user.

💡
¿De dónde saco la IP pública?

En la consola de AWS: EC2 → Instances → (selecciona tu instancia) → pestaña Details → "Public IPv4 address". Ojo: esa IP cambia cada vez que apagas y prendes la instancia, así que revísala justo antes de conectarte.

Windows PowerShell — tu equipo local
# La opcion -i indica cual es la llave (identity file) a usar # Formato: ssh -i <llave> <usuario>@<IP-publica> PS> ssh -i vockey.pem ec2-user@<IP-PUBLICA> # Solo la primera vez pregunta si confias en el servidor: escribe yes The authenticity of host '...' can't be established. Are you sure you want to continue connecting (yes/no)? yes # Si aparece este prompt, ya estas DENTRO del servidor RHEL [ec2-user@ip-172-31-37-145 ~]$
⚠
El puerto 22 debe estar abierto en el Security Group

Igual que el 3389 (RDP) para Windows, aquí AWS debe permitir el puerto 22 (SSH) en el Security Group de la instancia. Si no, la conexión se queda esperando y falla con Connection timed out.

Concepto
01 — SSH · sudo y usuarios
Usuario normal
vs. root

Entras como ec2-user, un usuario normal sin permisos de administrador. Para tareas de administración se antepone sudo (superuser do), que ejecuta ese comando con privilegios de root (el administrador total del sistema).

  • $ al final del prompt indica usuario normal.
  • # indicaría sesión como root.
  • Buenas prácticas: trabajar como usuario normal y usar sudo solo cuando es necesario. Nunca operar todo el tiempo como root.
✓
Verifica quién eres

Los comandos whoami (usuario actual) y hostname (nombre del equipo) te orientan apenas entras. Los usaremos constantemente.

02 — Comandos básicos
Bloque 02 · Base 3.1.3
Comandos básicos
y navegación

Ya estás dentro por SSH. Antes de configurar nada, aprende a moverte por la consola: en Linux todo cuelga de una única raíz, la barra /. No hay letras de unidad como C: o D: de Windows.

Concepto
02 — Comandos básicos · FHS
La estructura
de directorios

El estándar FHS (Filesystem Hierarchy Standard) define qué va en cada directorio. Los más importantes:

DirectorioQué contiene
/La raíz. Todo lo demás cuelga de aquí.
/rootCarpeta personal del usuario root.
/homeCarpetas personales de los usuarios normales (/home/ana).
/etcArchivos de configuración del sistema y servicios.
/varDatos variables: logs (/var/log), colas, sitios web.
/tmpArchivos temporales. Se borran al reiniciar.
/bin, /usrProgramas y comandos del sistema.
Pasos
02 — Comandos básicos · Navegación
Moverse y gestionar
archivos por CLI
Terminal — sesion SSH en el servidor
$ pwd # ¿donde estoy? -> /home/ec2-user $ ls -l # listar con detalle (permisos, dueño...) $ cd /var/log # cambiar de directorio $ cd ~ # volver a mi carpeta personal # Crear, copiar, mover, borrar $ mkdir proyecto # crear directorio $ touch proyecto/notas.txt # crear archivo vacio $ cp notas.txt copia.txt # copiar $ mv copia.txt /tmp/ # mover $ rm /tmp/copia.txt # borrar
✓
Leer la salida de ls -l

Una línea como -rw-r--r-- 1 ec2-user ec2-user 1024 nov 3 notas.txt te dice: tipo y permisos, dueño (ec2-user), grupo (ec2-user), tamaño y nombre. Ese primer bloque de letras son los permisos, que estudiamos en detalle en la próxima clase.

03 — Hostname
Bloque 03 · Criterio 3.1.2
Cambiar el
hostname

AWS asigna un nombre genérico tipo ip-172-31-37-145. Le ponemos un nombre descriptivo para identificar el servidor en la red. En Linux esto no requiere reiniciar.

Pasos
03 — Hostname · hostnamectl
Cambiar el nombre
con hostnamectl

En RHEL el hostname se gestiona con hostnamectl. El cambio es inmediato: no hace falta reiniciar el servidor.

Terminal — sesion SSH en el servidor
# Ver el hostname actual $ hostnamectl Static hostname: ip-172-31-37-145.ec2.internal # Asignar un nombre descriptivo (requiere sudo) $ sudo hostnamectl set-hostname linux-srv-rhel # Verificar el cambio $ hostnamectl Static hostname: linux-srv-rhel # El prompt nuevo aparece al reconectar o abrir otra sesion [ec2-user@linux-srv-rhel ~]$
💡
Convención de nombres

Usa solo minúsculas, números y guiones, sin espacios ni tildes. Un buen nombre describe el rol: linux-srv-rhel, web-prod, db-01.

04 — IP Fija
Bloque 04 · Criterio 3.1.2
Direccionamiento
IP

Por defecto la instancia toma su IP por DHCP. Vamos a fijarla de forma estática usando exactamente la misma IP privada que AWS ya asignó, calculando gateway y máscara desde el CIDR de la subred (justo lo de la Unidad 1).

Concepto
04 — IP Estática · Datos desde AWS
Los datos que
necesitas de AWS

Los mismos cuatro valores que usamos en Windows Server. Se obtienen desde la consola de AWS (EC2 → tu instancia → Details, y el CIDR desde el Subnet):

  • IP privada actual: la que AWS asignó, ej. 172.31.37.145. La reutilizas como IP fija.
  • CIDR de la subred: ej. 172.31.32.0/20. De aquí sale la máscara.
  • Gateway: dirección de red del CIDR + 1. Para 172.31.32.0/20 → 172.31.32.1.
  • DNS: 169.254.169.253 (resolver de AWS) y 8.8.8.8 como respaldo.
⚠
Usa exactamente la misma IP que AWS ya asignó

Si escribes una IP distinta o fuera del CIDR de la subred, el servidor pierde conectividad y se cae la sesión SSH. En la nube, la IP la manda AWS: solo la estamos fijando, no cambiando.

Pasos
04 — IP Estática · nmcli
Fijar la IP
con nmcli

RHEL gestiona la red con NetworkManager. Su herramienta de línea de comandos es nmcli.

Terminal — sesion SSH en el servidor
# 1. Ver las conexiones y el nombre de la interfaz $ nmcli connection show NAME UUID TYPE DEVICE System eth0 .... ethernet eth0 # 2. Fijar IP, gateway, DNS y metodo manual (una sola linea) $ sudo nmcli con mod "System eth0" \ ipv4.addresses 172.31.37.145/20 \ ipv4.gateway 172.31.32.1 \ ipv4.dns "169.254.169.253 8.8.8.8" \ ipv4.method manual # 3. Aplicar los cambios $ sudo nmcli con up "System eth0" # 4. Verificar $ ip addr show eth0 $ ping -c 3 8.8.8.8 # comprobar salida a internet
💡
Qué hace cada parte del comando

ipv4.addresses 172.31.37.145/20: la IP fija más la máscara en formato CIDR (el /20). ipv4.gateway: la puerta de enlace (el router de la subred). ipv4.dns "... ...": los servidores DNS; las comillas agrupan los dos en un solo valor. ipv4.method manual: le ordena a NetworkManager dejar de pedir IP por DHCP y usar estos valores fijos. La barra \ al final de cada línea solo significa "el comando continúa abajo"; puedes escribir todo en una sola línea si prefieres.

⚠
Si se cae la sesión SSH

Escribiste un valor incorrecto (IP, máscara o gateway). Reinicia la instancia desde la consola de AWS: al volver a DHCP recuperas el acceso y puedes reintentar con los valores correctos.

05 — Actualizaciones
Bloque 05 · Criterio 3.1.2
Actualizaciones
del sistema

Un servidor sin actualizar tiene vulnerabilidades conocidas. En RHEL el gestor de paquetes es dnf (evolución de yum). Con un solo comando dejamos el sistema al día. En la clase 3 profundizamos en gestión de paquetes.

Concepto + Pasos
05 — Actualizaciones · dnf update
Actualizar con
dnf / yum

En RHEL, dnf es el gestor de paquetes moderno; yum sigue funcionando como alias por compatibilidad. Ambos descargan e instalan software desde los repositorios oficiales.

Terminal — sesion SSH en el servidor
# Ver que actualizaciones hay disponibles $ sudo dnf check-update # Actualizar todo el sistema (-y responde "si" automaticamente) $ sudo dnf update -y Dependencies resolved. Upgrading : kernel, openssl, systemd ... Complete! # yum funciona igual (es un alias en RHEL) $ sudo yum update -y
💡
RPM está por debajo

dnf resuelve dependencias y descarga; internamente instala paquetes en formato RPM (Red Hat Package Manager). Ese es el criterio 3.1.4 que veremos en detalle en la clase 3.

⚠
Si se actualiza el kernel

Conviene reiniciar (sudo reboot) para cargar el nuevo kernel. La sesión SSH se cerrará; espera 1-2 minutos y reconéctate.

06 — Firewall
Bloque 06 · Criterio 3.1.2
Firewall
del sistema

El firewall controla qué tráfico entra y sale del servidor. En RHEL la herramienta es firewalld, que organiza las reglas en zonas y servicios. Abrimos solo lo necesario.

Concepto
06 — Firewall · firewalld
Qué es
firewalld

firewalld es el servicio de firewall de RHEL. En lugar de reglas sueltas, trabaja con zonas (perfiles de confianza) y servicios (grupos de puertos con nombre, ej. http = puerto 80).

  • Regla temporal: se pierde al reiniciar el servicio.
  • Regla permanente (--permanent): sobrevive reinicios. Requiere --reload para activarse.
⚠
Dos capas de firewall

En AWS conviven el Security Group (firewall de la nube) y firewalld (firewall del sistema operativo). Ambos deben permitir el tráfico. Si uno bloquea, la conexión falla. Mismo concepto que en Windows Server.

Pasos
06 — Firewall · firewall-cmd
Abrir puertos
con firewall-cmd

Como ejemplo, permitimos tráfico web (HTTP y HTTPS). Existen dos formas equivalentes de abrir acceso; a propósito usamos una de cada una para que veas ambas.

Terminal — sesion SSH en el servidor
# Verificar que firewalld este activo $ sudo systemctl status firewalld # Permitir HTTP (puerto 80) de forma permanente $ sudo firewall-cmd --permanent --add-service=http # Permitir HTTPS por numero de puerto (puerto 443) $ sudo firewall-cmd --permanent --add-port=443/tcp # Recargar para aplicar las reglas permanentes $ sudo firewall-cmd --reload # Verificar que quedaron activas $ sudo firewall-cmd --list-all services: cockpit dhcpv6-client ssh http ports: 443/tcp
💡
Las dos formas: por servicio o por puerto

--add-service=<nombre> usa un nombre conocido (http, https, ssh) y firewalld ya sabe qué puerto le corresponde (http = 80). Es más legible. --add-port=<numero>/<protocolo> abre el puerto exacto (443/tcp), útil cuando el servicio no tiene nombre o quieres control fino. Las dos hacen lo mismo; ambas se combinan con --permanent para sobrevivir reinicios.

✓
No cierres el puerto 22

El servicio ssh ya está permitido por defecto. Nunca lo quites: es tu única vía de acceso al servidor. Si lo bloqueas, pierdes la conexión.
