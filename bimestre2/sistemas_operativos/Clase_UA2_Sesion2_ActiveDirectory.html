01 — Active Directory
Bloque 01
¿Qué es
Active Directory?

El servicio que convierte un servidor suelto en el centro de control de toda una red: usuarios, equipos y permisos administrados desde un solo lugar.

Concepto
01 — Active Directory · Qué es
Un directorio
centralizado

Active Directory (AD) es el servicio de directorio de Microsoft. Guarda en una base de datos toda la información de la red — usuarios, equipos, grupos, impresoras — y permite administrarla de forma centralizada.

El problema que resuelve: sin AD, cada equipo tiene sus propios usuarios locales. Si una empresa tiene 50 computadores, hay que crear y mantener las cuentas 50 veces. Con AD, creas el usuario una vez y puede iniciar sesión en cualquier equipo del dominio.

Sin dominio (grupo de trabajo)

Usuarios locales en cada PC. 50 equipos = 50 administraciones separadas. Sin políticas comunes.

Con dominio (Active Directory)

Un usuario inicia sesión en cualquier equipo. Políticas aplicadas desde un punto. Administración central.

💡
El rol técnico se llama AD DS

En Windows Server, el rol que instalas se llama Active Directory Domain Services (AD DS). "Active Directory" es el nombre del servicio; "AD DS" es el rol concreto que activas en el servidor.

Concepto
01 — Active Directory · Vocabulario
Vocabulario
que usaremos hoy
  • Dominio: el conjunto de usuarios, equipos y recursos administrados juntos. El nuestro será inacap.local.
  • Controlador de Dominio (DC): el servidor que ejecuta AD DS y guarda la base de datos del dominio. Es la "autoridad" que valida quién puede entrar.
  • DNS: el servicio que traduce nombres a IPs. AD depende de DNS para funcionar — los clientes encuentran al DC preguntándole al DNS.
  • Unidad Organizativa (OU): una carpeta lógica dentro del dominio para agrupar usuarios y equipos (por ejemplo, por departamento).
  • Directiva de Grupo (GPO): un conjunto de reglas de configuración que se aplican automáticamente a los objetos de una OU.
⚠
AD y DNS van siempre juntos

Cuando promovamos el servidor a DC, Windows instalará DNS automáticamente. Si DNS falla, el dominio entero deja de funcionar: los clientes no encuentran al DC. Recuérdalo cuando un equipo "no ve" el dominio.

Arquitectura
01 — Active Directory · El panorama
Cómo se ve
un dominio

El Controlador de Dominio es el centro: ejecuta AD DS (la base de datos) y DNS (que permite encontrarlo). Los equipos se unen al dominio y, desde ese momento, cualquier cuenta puede iniciar sesión en cualquiera de ellos.

Antes de instalar

Antes de instalar cualquier rol, necesitas configurar correctamente la red. Esta sección explica cada valor y por qué importa — especialmente lo que cambia según tu subred en AWS.

Panorama
¿Qué estás haciendo? · Secuencia completa
Los 4 momentos
de configuración de red

Para tener un DC funcional con acceso a internet, vas a pasar por cuatro configuraciones de red distintas. Cada una tiene una razón específica:

1
IP estática + DNS apuntando a AWS
El servidor necesita IP fija antes de ser DC. DNS apunta al resolver de AWS (172.31.0.2) para mantener internet mientras instalas el rol.
2
Instalar AD DS y promover a DC
El rol se instala y el servidor reinicia como Controlador de Dominio con la zona inacap.local.
3
Cambiar DNS a sí mismo (127.0.0.1)
El DC ahora aloja la zona inacap.local. Debe preguntarse a sí mismo, no a AWS, cuando algo busca el dominio.
4
Agregar forwarder → internet vuelve
El forwarder le indica al DNS local: "todo lo que no sepas resolver, reenvíalo a 172.31.0.2".
💡
¿Por qué no dejar el DNS de AWS desde el principio?

Porque el DC debe ser la autoridad de inacap.local. Si apunta a AWS, los clientes le preguntarán al DC y él redirigirá a AWS, que no conoce tu dominio — todo falla. El forwarder resuelve esto sin sacrificar internet.

Paso 1
¿Qué estás haciendo? · IP estática en AWS
La máscara
correcta para AWS

Antes de escribir cualquier valor, verifica el CIDR de tu subred en la consola de AWS: VPC → Subnets → columna IPv4 CIDR. El CIDR determina la máscara:

/24 — ejemplo genérico

Máscara: 255.255.255.0
Rango usable: .1 a .254

/20 — default en AWS Academy

Máscara: 255.255.240.0
Rango usable: .80.1 a .95.254

Con la subred 172.31.80.0/20, la configuración queda:

Adaptador de red → TCP/IPv4 → PropiedadesIP address: 172.31.80.10 Subnet mask: 255.255.240.0 Default gateway: 172.31.80.1 ← base de la subred + 1 Preferred DNS server: 172.31.0.2 ← base de la VPC + 2 (antes de promover)
⚠
Gateway de la subred, DNS de la VPC — no los confundas

El gateway usa la base de la subred + 1: 172.31.80.1. El resolver DNS de AWS usa la base de la VPC + 2: 172.31.0.2. Son direcciones distintas.

DNS del DC
03 — Promoción · DNS del Controlador de Dominio
El DC apunta su
DNS a sí mismo

Antes de promover, tu servidor usaba el DNS de AWS para tener internet — y estaba bien. Pero un DC debe apuntar su DNS preferido a sí mismo (127.0.0.1 o su propia IP estática), porque ahora él aloja la zona inacap.local.

⚡
"Pierde internet" al poner 127.0.0.1 — es normal

No pierdes internet de verdad: falla la resolución de nombres. El ping a una IP funciona, pero los nombres (google.com) no resuelven. Tu DNS local sabe resolver inacap.local, pero no sabe a quién preguntarle por los nombres de internet. Se arregla con un forwarder.

El forwarder le dice a tu DNS: "lo que no sepas resolver, reenvíalo al DNS de AWS". En DNS Manager → clic derecho en el servidor → Properties → pestaña Forwarders → Edit, o por PowerShell:

PowerShell — agregar forwarder al resolver de AWSAdd-DnsServerForwarder -IPAddress 10.0.0.2
💡
¿Cuál es la IP del resolver de AWS?

Es la base del CIDR de tu VPC + 2: una VPC 10.0.0.0/16 → 10.0.0.2; una 172.31.0.0/16 → 172.31.0.2. También funciona 169.254.169.253 en cualquier VPC.

DNS del DC
03 — Promoción · Cómo viaja una consulta DNS
Cómo resuelve
el DNS del DC

El DC resuelve dos tipos de consulta de forma distinta. Lo que es del dominio lo responde él mismo; lo de internet lo reenvía al forwarder. Esto explica por qué, sin forwarder, "se cae internet" pero el dominio sigue funcionando:

💡
Sin forwarder solo falla la fila de abajo

El dominio (fila verde) siempre funciona porque el DC tiene la zona. Internet (fila naranja) solo funciona si configuraste el forwarder. Por eso el síntoma es "anda el dominio pero no internet", nunca al revés.

DNS del DC
03 — Promoción · Errores a evitar
Dos errores que
rompen el dominio
✗
No pongas AWS como DNS secundario en el DC

La tentación es dejar 127.0.0.1 como primario y 10.0.0.2 como secundario "por si acaso". No lo hagas: Windows alterna entre ambos de forma impredecible, y cuando le toca preguntarle a AWS por inacap.local, AWS no lo conoce y AD empieza a fallar de forma intermitente — lo más difícil de depurar. El DC apunta solo a sí mismo; el forwarder se encarga de internet.

⏱
No pongas 127.0.0.1 antes de promover

Si apuntas a ti mismo antes de que exista el rol DNS, no hay nada escuchando y no resuelve nada. Deja el DNS de AWS hasta terminar la promoción; recién ahí cambias a 127.0.0.1 y agregas el forwarder.

Verifica el estado final del DC:

PowerShell — comprobar DNS y resoluciónPS C:\Users\Administrator> Get-Service DNS Status Name DisplayName ------ ---- ----------- Running DNS DNS Server PS C:\Users\Administrator> Resolve-DnsName inacap.local # resuelve local PS C:\Users\Administrator> Resolve-DnsName google.com # resuelve via forwarder
✓
Si ambos resuelven, el DC quedó perfecto

El primero confirma que el DNS local aloja tu dominio; el segundo, que el forwarder reenvía internet. Verifica con ipconfig /all que el DNS preferido sea 127.0.0.1 — el asistente a veces lo deja así solo, pero no siempre.

04 — Cliente
Bloque 04
Unir el
cliente al dominio

El dominio existe, pero está vacío de equipos. Ahora incorporamos la segunda máquina — el equipo cliente — para que sus usuarios puedan iniciar sesión con cuentas del dominio.

Topología
04 — Cliente · Cómo se conectan en AWS
El mapa
de la red

Las dos instancias viven en la misma subred de tu VPC. Para que se "vean", el Security Group debe permitir el tráfico interno, y el cliente debe usar al DC como su DNS. Así queda el armado:

⚠
Las IPs son de ejemplo

Usa las que te asignó AWS a cada instancia. Lo importante es el patrón: misma subred, Security Group permitiendo el tráfico entre ellas, y el DNS del cliente apuntando a la IP privada del DC.

Paso clave
04 — Cliente · DNS apuntando al DC
El paso que
todos olvidan

Antes de unir el cliente, su DNS preferido debe apuntar a la IP privada del Controlador de Dominio. Sin esto, el cliente no encuentra el dominio y la unión falla.

1
En el cliente: Configuración del adaptador de red
Propiedades de TCP/IPv4 → DNS preferido = IP privada del DC (ej: 10.0.1.10).
2
Verifica conectividad con el DC
ping 10.0.1.10 y luego nslookup inacap.local deben responder desde el cliente.
⚡
En AWS: el Security Group debe permitir tráfico interno

Las dos instancias deben estar en la misma subred y el Security Group debe permitir todo el tráfico entre ellas. Lo más simple: agrega una regla de entrada All traffic con Source = el propio Security Group. Sin esto, el ping y la unión al dominio fallan aunque el DNS esté bien.

Permite aplicar una directiva común a toda la institución enlazándola a INACAP, y directivas específicas por departamento enlazándolas a cada OU hija. Esa jerarquía es justo lo que el ES2 pide demostrar con gpresult.

06 — Directivas
Bloque 06
Directivas de
Grupo (GPOs)

La pieza que demuestra el poder de un dominio: defines una regla una vez, la enlazas a una OU, y se aplica automáticamente a todos sus usuarios y equipos.

Concepto
06 — Directivas · Plan
Las 4 GPOs
que crearemos

Una GPO enlazada a la OU raíz INACAP afecta a todos. Una GPO enlazada a una OU de departamento afecta solo a ese departamento. Así, cada usuario recibe la GPO raíz + la GPO de su OU:

1
GPO-Fondo-Corporativo → enlazada a OU INACAP
Fija un fondo de escritorio común. Afecta a los tres departamentos.
2
GPO-Bloquear-Panel → enlazada a OU Finanzas
Oculta el Panel de Control y la Configuración. Solo para Finanzas.
3
GPO-Mensaje-Inicio → enlazada a OU TI
Muestra un mensaje legal al iniciar sesión. Solo para TI.
4
GPO-Ocultar-Unidad-C → enlazada a OU RRHH
Oculta la unidad C: en el Explorador. Solo para RRHH.
💡
Por qué este diseño

Con una GPO en la raíz y una por OU, gpresult /r mostrará 2 GPOs aplicadas por usuario (la raíz + la de su departamento). Ese es exactamente el resultado que pide demostrar la rúbrica del ES2.

Herencia
06 — Directivas · Cómo se heredan
Cada usuario
recibe 2 GPOs

Una GPO se aplica a la OU donde está enlazada y a todo lo que cuelga de ella. Como hay una GPO en la raíz INACAP y una en cada OU de departamento, cada usuario hereda exactamente dos: la de la institución y la de su área.

✓
Por eso gpresult muestra 2 GPOs por usuario

Ejemplo: jperez recibe GPO-Fondo-Corporativo (heredada de la raíz INACAP) + GPO-Bloquear-Panel (de su OU Finanzas). Las líneas rojas punteadas muestran cómo baja cada directiva hasta el usuario.

Pasos

paso a paso

Abre Group Policy Management (Server Manager → Tools, o ejecuta gpmc.msc). El flujo es el mismo para las cuatro:

1

3

⚠
Configuración de Usuario vs. de Equipo

Las directivas de "User Configuration" aplican al usuario sin importar el equipo; las de "Computer Configuration" aplican al equipo sin importar quién entre. El fondo de escritorio y el bloqueo de panel van en User Configuration. Elige bien la rama o la GPO "no tendrá efecto".
