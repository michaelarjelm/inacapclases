Conceptos fundamentales

Dato, información y conocimiento

Tres conceptos relacionados pero distintos que forman la base de cualquier sistema de información.

  • Dato: hecho crudo, sin contexto ni significado por sí solo.
  • Información: datos procesados y organizados con un contexto que les da significado.
  • Conocimiento: información interpretada y aplicada para tomar decisiones.
Clave: los datos son la materia prima. Sin procesamiento, no generan valor por sí solos.

Conceptos fundamentales

Procesamiento de datos

El procesamiento de datos es el conjunto de operaciones que transforman datos crudos en información útil para una organización.

  • Recolección: captura de datos desde sensores, formularios, transacciones.
  • Almacenamiento: persistencia organizada y accesible.
  • Procesamiento: cálculo, filtrado, agregación, transformación.
  • Distribución: entrega de la información al usuario correcto.
El DBMS (Sistema Gestor de BD) es el software que automatiza todo este ciclo.

Conceptos fundamentales

¿Qué es una Base de Datos?

Una base de datos es una colección de datos organizada, persistente y relacionada, diseñada para ser consultada y modificada de forma eficiente por múltiples usuarios o sistemas.

  • Organizada: estructura definida (tablas, documentos, grafos…)
  • Persistente: los datos sobreviven al apagado del sistema.
  • Compartida: múltiples usuarios acceden simultáneamente.
  • Controlada: con reglas de integridad y permisos de acceso.

Conceptos fundamentales

Instancia vs Esquema

Dos conceptos que describen la misma base de datos desde perspectivas distintas — uno es permanente, el otro cambia constantemente.

  • Esquema: la definición estructural de la BD — tablas, columnas, tipos de dato y restricciones. Cambia raramente. Es el "plano del edificio".
  • Instancia: el contenido actual de la BD en un momento dado. Cambia con cada INSERT, UPDATE o DELETE. Es "el edificio habitado".
Analogía: el esquema es el molde, la instancia es el chocolate que hay dentro en este momento.

Conceptos fundamentales — Diseño

Diagrama Entidad-Relación

Antes de crear tablas se diseña el modelo. El DER representa visualmente qué datos existen y cómo se relacionan, de forma independiente del DBMS.

  • Entidad: objeto del mundo real con existencia propia (Cliente, Pedido, Producto).
  • Atributo: característica de la entidad. El atributo marcado como PK es la clave primaria.
  • Relación: vínculo semántico entre entidades (el rombo).
  • Cardinalidad: cuántas instancias participan en cada extremo — 1:1 · 1:N · N:M.
El DER se diseña primero en papel → luego se traduce a tablas SQL. Es el plano del edificio antes de construirlo.

Cinco formas distintas de estructurar y relacionar los datos.

Modelos de BD — 01

Modelo Relacional

Organiza los datos en tablas (relaciones) con filas y columnas. Las tablas se conectan mediante claves foráneas. Es el modelo dominante en sistemas empresariales.

  • Estructura: tablas con esquema fijo.
  • Integridad: restricciones PK, FK, UNIQUE, CHECK.
  • Lenguaje: SQL estándar.
  • Transacciones: propiedades ACID garantizadas.
Ejemplos: PostgreSQL, MySQL, Oracle, SQL Server, MariaDB.

Modelo Relacional — Fundamento

Propiedades ACID

Las propiedades ACID son las garantías que todo DBMS relacional ofrece para que las transacciones sean confiables incluso ante fallos de hardware o accesos concurrentes.

A
Atomicidad
La transacción es "todo o nada" — si falla un paso, se deshacen todos los cambios.
→ Si el débito a Ana falla, el crédito a Pedro jamás ocurre.
C
Consistencia
La BD siempre pasa de un estado válido a otro, respetando todas las reglas de integridad.
→ La suma de saldos de Ana + Pedro es idéntica antes y después de la transferencia.
I
Aislamiento
Las transacciones concurrentes no se ven entre sí hasta que terminan por completo.
→ Nadie ve la cuenta de Ana descontada sin que Pedro ya haya recibido el dinero.
D
Durabilidad
Una vez confirmado el COMMIT, el cambio persiste aunque el sistema falle inmediatamente después.
→ Tras el COMMIT, aunque el servidor caiga, la transferencia quedó registrada para siempre.
Transacción: secuencia de operaciones que se ejecutan como una unidad indivisible. Empieza con BEGIN y termina con COMMIT (confirmar) o ROLLBACK (deshacer).
Ana transfiere $50.000 a Pedro
Dos operaciones, una sola unidad — si falla el paso 2, el paso 1 se deshace.
-- inicio de transacción
BEGIN;
UPDATE cuentas SET saldo = saldo - 50000
  WHERE id = 1;
UPDATE cuentas SET saldo = saldo + 50000
  WHERE id = 2;
COMMIT;
A — Atomicidad
Si falla el 2° UPDATE → ROLLBACK del 1°
C — Consistencia
Suma total de saldos igual antes y después
I — Aislamiento
Otra sesión no ve el débito sin el crédito
D — Durabilidad
Tras COMMIT, persiste aunque caiga el servidor

Modelos de BD — 02

Modelo Clave-Valor

La estructura más simple: cada dato se almacena como un par clave única → valor. El valor puede ser cualquier cosa (string, número, JSON, imagen binaria).

  • Fortaleza: velocidad extrema de lectura/escritura.
  • Debilidad: no permite consultas complejas sobre el valor.
  • Uso ideal: caché, sesiones de usuario, contadores en tiempo real.
Ejemplos: Redis, DynamoDB, Riak, Memcached.
Almacén Redis (ejemplo)

cache:prod:55→{"nombre":"Laptop","precio":499}
token:reset:abc9→expires:1748390400

Modelos de BD — 03

Modelo Documental

Los datos se almacenan como documentos semi-estructurados (JSON, BSON, XML). Cada documento puede tener una estructura distinta, sin esquema rígido.

  • Fortaleza: esquema flexible, fácil de escalar horizontalmente.
  • Debilidad: integridad referencial manual, sin JOINs nativos eficientes.
  • Uso ideal: catálogos de productos, CMS, perfiles de usuario.
Ejemplos: MongoDB, CouchDB, Firestore, Amazon DocumentDB.
Documento MongoDB (colección: productos)
{ "_id": "prod_0042", "nombre": "Laptop Pro 15", "precio": 899990, "especificaciones": { "ram": "16GB", "ssd": "512GB" }, "tags": ["electronico","oferta"] }

Modelos de BD — 04

Modelo de Grafo

Los datos se representan como nodos (entidades) y aristas (relaciones). Cada nodo y arista pueden tener propiedades adicionales.

  • Fortaleza: traversal eficiente de relaciones complejas y profundas.
  • Debilidad: consultas simples son más complejas de expresar.
  • Uso ideal: redes sociales, motores de recomendación, detección de fraude.
Ejemplos: Neo4j, Amazon Neptune, ArangoDB, TigerGraph.

Modelos de BD — 05

Modelo Orientado a Objetos

Los datos se almacenan como objetos con atributos y métodos, siguiendo el paradigma de la POO. Soporta herencia, encapsulamiento y polimorfismo directamente en la BD.

  • Fortaleza: mapeo directo entre BD y código orientado a objetos.
  • Debilidad: menor adopción, pocas herramientas maduras.
  • Uso ideal: CAD/CAM, multimedia, ingeniería, simulaciones.
Ejemplos: ObjectDB, db4o, Versant, GemStone.

Modelos de BD — 06 · Emergente

Modelo Vectorial

Los datos se almacenan como vectores numéricos de alta dimensión (embeddings) que representan el significado semántico de textos, imágenes o audio. La búsqueda no es por igualdad exacta, sino por similitud.

  • Fortaleza: búsqueda semántica — "encuentra documentos con significado similar a esta pregunta".
  • Debilidad: no reemplaza consultas transaccionales ni relacionales.
  • Uso ideal: sistemas RAG de IA generativa, búsqueda semántica, reconocimiento facial, recomendaciones por contenido.
Ejemplos: Pinecone, Weaviate, Chroma, Qdrant, pgvector (extensión de PostgreSQL). ChatGPT, Claude y Gemini los usan para memoria y búsqueda de contexto.

Modelos de BD — ¿Por qué tantos tipos?

Teorema CAP

En un sistema de BD distribuido, es imposible garantizar simultáneamente las tres propiedades del teorema CAP. Solo se pueden elegir dos de tres.

  • Consistencia (C): todos los nodos ven exactamente los mismos datos al mismo tiempo.
  • Disponibilidad (A): toda consulta recibe una respuesta, aunque no sea la más reciente.
  • Tolerancia a particiones (P): el sistema funciona aunque fallen conexiones entre nodos.
En la práctica, las redes fallan — por eso P es obligatoria en sistemas distribuidos. La elección real es entre C+P (consistente, puede rechazar lecturas) o A+P (siempre responde, puede dar datos levemente desactualizados).

Unidad 1 — Bloque 03

Nuestro foco:
Modelo Relacional

De todos los modelos vistos, el relacional es el más extendido en la industria — banca, ERP, sistemas académicos, salud. Aprender a consultarlo con SQL es la habilidad base de cualquier profesional TI.

Lenguaje de consulta — DML

Las 4 operaciones SQL fundamentales
SELECT — Consultar datos
SELECT nombre, saldo
FROM clientes
WHERE ciudad = 'Santiago'
ORDER BY saldo DESC;
Devuelve filas que cumplen la condición, en el orden indicado.
INSERT — Agregar datos
INSERT INTO clientes
  (id, nombre, ciudad, saldo)
VALUES
  (4, 'Luis Vega', 'Temuco', 320000);
Agrega una nueva fila a la tabla.
UPDATE — Modificar datos
UPDATE clientes
SET saldo = saldo + 50000,
    ciudad = 'Valdivia'
WHERE id = 4;
Modifica filas existentes que cumplen la condición.
DELETE — Eliminar datos
DELETE FROM clientes
WHERE id = 4;

-- ¡sin WHERE elimina TODAS las filas!
Elimina filas. Siempre usar WHERE en producción.
DML vs DDL: SELECT / INSERT / UPDATE / DELETE son comandos DML (manipulación de datos). CREATE TABLE, ALTER TABLE y DROP TABLE son DDL (definición de estructura) — los veremos en detalle en la próxima unidad.

El modelo ANSI/SPARC de tres niveles y cómo el DBMS media entre ellos.

Arquitectura DBMS

¿Qué hace un DBMS?

Un DBMS (Database Management System) es el software que gestiona el almacenamiento, acceso, seguridad y consistencia de los datos. No es la base de datos — es el motor que la administra.

  • Procesa consultas: analiza, optimiza y ejecuta sentencias SQL.
  • Gestiona transacciones: garantiza propiedades ACID.
  • Controla concurrencia: múltiples usuarios sin conflictos.
  • Recuperación ante fallos: logs y rollback automático.
  • Gestiona usuarios: autenticación, roles y permisos.
El DBMS expone sus funciones a través del catálogo del sistema — un repositorio interno de metadatos sobre todas las tablas, columnas, índices y usuarios.

Arquitectura DBMS — Nivel 3

Nivel Externo

Es la capa más cercana al usuario. Cada usuario o aplicación ve solo la parte de la base de datos que le corresponde — una vista personalizada del esquema.

  • Un vendedor ve precios y stock, pero no costos de producción.
  • Un contador ve transacciones pero no datos personales de clientes.
  • Las vistas aíslan a los usuarios de la complejidad interna.
Puede existir n vistas distintas del mismo esquema conceptual, una por rol de usuario.

Arquitectura DBMS — Nivel 2

Nivel Conceptual

Define qué datos existen y cómo se relacionan lógicamente, sin preocuparse por cómo se almacenan físicamente. Es el esquema compartido por toda la organización.

  • Contiene entidades, atributos, relaciones y restricciones.
  • Es independiente del hardware y del DBMS subyacente.
  • Cambios en el almacenamiento físico no afectan este nivel.
En bases de datos relacionales, el esquema conceptual son las tablas, columnas, PK y FK.

Arquitectura DBMS — Nivel 1

Nivel Interno

Describe cómo se almacenan físicamente los datos: archivos en disco, estructuras de índices, métodos de acceso y organización de páginas.

Arquitectura DBMS — Beneficio clave

Independencia de datos

La razón de fondo por la que existen los 3 niveles ANSI/SPARC. La independencia de datos permite modificar un nivel sin afectar los niveles superiores.

  • Independencia física: puedo cambiar cómo se almacenan los datos (migrar de HDD a SSD, reorganizar índices, cambiar de servidor) sin modificar el esquema lógico ni las aplicaciones.
  • Independencia lógica: puedo agregar una nueva columna o tabla al esquema lógico sin romper las vistas de usuario ni las aplicaciones existentes.
Sin independencia de datos, cada cambio de hardware o estructura obligaría a reescribir todas las aplicaciones que acceden a la BD.

Arquitectura DBMS — Actores

Roles en un sistema de BD

Un sistema de base de datos no es solo software — involucra personas con responsabilidades distintas que interactúan con el DBMS en niveles diferentes. Cada rol tiene acceso solo a lo que necesita: es el principio de mínimo privilegio.

En equipos pequeños una misma persona puede cubrir varios roles. En organizaciones grandes, son cargos separados con responsabilidades y contratos distintos.
🛡
DBA Database Administrator
Diseña el esquema, gestiona usuarios, optimiza rendimiento y controla la seguridad. Acceso total.
CREATE · DROP · GRANT · BACKUP
💻
Desarrollador
Escribe consultas, crea vistas y lógica de negocio. Acceso controlado en entornos de desarrollo.
SELECT · INSERT · UPDATE · DELETE
👤
Usuario Final
Interactúa a través de una aplicación, sin escribir SQL. Ve solo la vista que le corresponde.
SELECT (sobre vistas restringidas)
📊
Analista de Datos
Realiza consultas complejas y reportes. Solo lectura sobre producción o réplica analítica.
SELECT · GROUP BY · JOIN · HAVING

Seguridad — Amenazas

Principales amenazas

Conocer las amenazas es el primer paso para proteger una base de datos. No todas son externas.

Regla 80/20: la mayoría de las brechas de datos involucran acceso interno no autorizado o credenciales comprometidas, no ataques externos sofisticados.
  • 🔒
    Inyección SQL
    Código malicioso en campos de entrada que manipula o extrae datos de la BD.
  • 👤
    Acceso no autorizado
    Usuarios con más permisos de los necesarios o credenciales débiles/comprometidas.
  • 🔥
    Pérdida o corrupción
    Fallos de hardware, errores de software o eliminación accidental sin respaldo.
  • 🔎
    Intercepción de datos
    Tráfico no cifrado entre la aplicación y la BD capturado por terceros.

Seguridad — Contramedidas

Buenas prácticas

La seguridad en BD es una capa, no un interruptor. Se construye combinando múltiples controles complementarios.

Principio de mínimo privilegio: cada usuario o aplicación debe tener solo los permisos estrictamente necesarios para su función.
  • 🛡
    Control de acceso por roles
    Asignar permisos (SELECT, INSERT, UPDATE) por rol, no por usuario individual.
  • 🔐
    Cifrado de datos
    En reposo (columnas sensibles) y en tránsito (TLS entre app y BD).
  • 💾
    Copias de respaldo (backups)
    Backup periódico con prueba de restauración verificada. Regla 3-2-1.
  • 📋
    Auditoría y logs
    Registrar quién accede a qué y cuándo — trazabilidad ante incidentes.

Seguridad — Marco Legal en Chile

Ley 19.628 y Ley 21.719
Aspecto Ley 19.628 (1999 — vigente) Ley 21.719 (2024 — modernización)
¿Qué es? Primera ley chilena de protección de datos personales. Regula su recolección, almacenamiento y uso por entidades públicas y privadas. Nueva ley que moderniza la legislación chilena acercándola al estándar GDPR europeo. Crea la Agencia de Protección de Datos Personales.
Derechos Acceso, modificación, cancelación y bloqueo de datos personales (derechos ARCB). Amplía a: acceso, rectificación, supresión, portabilidad, oposición y a no ser objeto de decisiones automatizadas.
Brechas No establece obligación de notificar brechas de seguridad. Obliga a notificar brechas a la Agencia y a los afectados en un plazo máximo de 72 horas.
Sanciones Sanciones limitadas, poco disuasivas en la práctica. Multas de hasta 10.000 UTM por infracción grave. Sanciones proporcionales al daño y tamaño de la organización.
Relevancia BD Toda base de datos que almacene datos personales de ciudadanos chilenos debe cumplir con esta normativa — independiente del sector. El DBA es responsable de implementar los controles técnicos.
Para la evaluación: identifica qué datos personales gestiona tu sector asignado y qué obligaciones impone la Ley 21.719 a las organizaciones de ese sector.
