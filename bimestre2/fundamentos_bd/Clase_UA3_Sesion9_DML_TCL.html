01 - INSERT · La anatomía
Meter una
fila

Insertar es agregar una fila a una tabla. Le dices en qué columnas y con qué valores, en el mismo orden.

INSERT INTO socio (id_socio, nombre, email)
VALUES (1, 'Ana Perez', 'ana@mail.cl');
Texto y fechas: con comillas

El texto va entre comillas simples: 'Ana Perez'. Los números van sin comillas: 1. Una fecha se escribe DATE '2026-07-08' (formato AÑO-MES-DÍA).

Nombrar columnas es lo pro

Puedes omitir la lista de columnas, pero entonces debes dar todos los valores en el orden exacto de la tabla. Nombrarlas evita errores: hazlo siempre.

💡
Los DEFAULT trabajan solos

Si una columna tiene DEFAULT (como copias o fecha_prestamo), puedes no mencionarla y Oracle pone el valor por defecto. Solo nombra las columnas que quieras llenar tú.

Un error clásico de internet

En muchos tutoriales de MySQL se meten varias filas en un solo INSERT con comas. En Oracle clásico no: cada fila es su propia sentencia terminada en ;. Si copias ese truco, da error.

02 - INSERT con FK · El orden manda
No prestes a un
socio fantasma

PRESTAMO tiene dos claves foráneas: apunta a un socio y a un libro que ya deben existir. Si intentas prestar al socio 99 y no hay socio 99, la base lo rechaza.

-- id_socio 99 no existe todavía
INSERT INTO prestamo (id_prestamo, id_socio, id_libro) VALUES (1, 99, 1);
ORA-02291: integrity constraint violated - parent key not found
🔑
Regla de oro del poblado

Se llenan primero las tablas padre (SOCIO, LIBRO) y después la hija (PRESTAMO). Es la misma regla del orden de creación de ayer: nunca puedes apuntar a algo que no está.

03 - TCL · El corazón de hoy
Guardar o
deshacer

Cuando insertas, borras o modificas, el cambio está en un borrador: lo ves tú, pero todavía no es definitivo. Dos órdenes deciden su destino:

Orden TCLQué hace
COMMITConfirma. Los cambios quedan grabados para siempre. No hay vuelta atrás.
ROLLBACKDeshace todo lo hecho desde el último COMMIT. Como un Ctrl+Z hasta el último guardado.
💾
La analogía del Word

Escribes en el documento (INSERT/UPDATE/DELETE), pero hasta que no le das Guardar (COMMIT) nada es permanente. Si te arrepientes antes de guardar, cierras sin guardar (ROLLBACK) y vuelve como estaba.

⚠
Por qué esto funciona aquí

SQL Developer no confirma solo: tú decides cuándo. Por eso el ROLLBACK sirve de red de seguridad. (En herramientas online el COMMIT es automático y no podrías deshacer.)

20:36 · 12 min Teclado 3
Ahora tú: deshaz
y luego confirma

Vamos a ver la magia en vivo. Inserta un socio de prueba, míralo, y bórralo con ROLLBACK sin que quede rastro:

-- 1. Socio de prueba
INSERT INTO socio (id_socio, nombre, email) VALUES (99, 'Prueba Borrame', 'x@x.cl');
SELECT * FROM socio; -- aparece el 99
-- 2. Me arrepiento
ROLLBACK;
SELECT * FROM socio; -- el 99 DESAPARECIÓ
-- 3. Ahora sí, los datos buenos: confírmalos para siempre
COMMIT;
📝
El momento aha

El socio 99 existió y luego dejó de existir sin que lo borraras a mano: el ROLLBACK reversó el INSERT. Ese COMMIT final graba de verdad los 3 socios, 3 libros y 2 préstamos que poblaste hoy.

04 - UPDATE y DELETE · Cambiar y quitar
El WHERE
te salva la vida

UPDATE cambia datos existentes; DELETE elimina filas. Los dos usan WHERE para decir a cuáles. Y ahí está el peligro.

-- Corregir el email del socio 1
UPDATE socio SET email = 'ana.perez@mail.cl' WHERE id_socio = 1;
-- Eliminar el préstamo 2
DELETE FROM prestamo WHERE id_prestamo = 2;
☠
El error que borra la tabla entera

Si olvidas el WHERE, el cambio cae sobre TODAS las filas. Un DELETE FROM socio; sin WHERE vacía la tabla completa. Regla: escribe el WHERE antes que el resto.

⚠
Y aquí se conecta con el TCL

¿Borraste de más y todavía no diste COMMIT? ROLLBACK y vuelve todo. Por eso se confirma solo cuando estás seguro. También hay orden con FK: no puedes borrar un SOCIO si un PRESTAMO lo usa (ORA-02292); borra primero el hijo.

Setup
Antes del banco · Crea las tablas de la tienda
El modelo que vas a poblar

El banco usa una tienda propia, distinta de la biblioteca. Pega este script una sola vez para crear sus cinco tablas y luego dedícate al DML. Fíjate en el orden: primero las padres (CATEGORIA, CLIENTE), después las hijas.

CREATE TABLE categoria (
id_categoria NUMBER CONSTRAINT pk_categoria PRIMARY KEY,
nombre VARCHAR2(50) NOT NULL);
CREATE TABLE cliente (
id_cliente NUMBER CONSTRAINT pk_cliente PRIMARY KEY,
nombre VARCHAR2(120) NOT NULL,
email VARCHAR2(100) UNIQUE,
ciudad VARCHAR2(50),
fecha_registro DATE DEFAULT SYSDATE);
CREATE TABLE producto (
id_producto NUMBER CONSTRAINT pk_producto PRIMARY KEY,
nombre VARCHAR2(80) NOT NULL,
precio NUMBER CHECK (precio > 0),
stock NUMBER DEFAULT 0 CHECK (stock >= 0),
id_categoria NUMBER,
CONSTRAINT fk_producto_categoria FOREIGN KEY (id_categoria) REFERENCES categoria(id_categoria));
CREATE TABLE pedido (
id_pedido NUMBER CONSTRAINT pk_pedido PRIMARY KEY,
id_cliente NUMBER NOT NULL,
fecha DATE DEFAULT SYSDATE,
estado VARCHAR2(20) DEFAULT 'PENDIENTE',
total NUMBER CHECK (total >= 0),
CONSTRAINT fk_pedido_cliente FOREIGN KEY (id_cliente) REFERENCES cliente(id_cliente));
CREATE TABLE detalle (
id_detalle NUMBER CONSTRAINT pk_detalle PRIMARY KEY,
id_pedido NUMBER NOT NULL,
id_producto NUMBER NOT NULL,
cantidad NUMBER CHECK (cantidad > 0),
precio_unitario NUMBER CHECK (precio_unitario > 0),
CONSTRAINT fk_detalle_pedido FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido),
CONSTRAINT fk_detalle_producto FOREIGN KEY (id_producto) REFERENCES producto(id_producto));
📁
Orden de poblado

CATEGORIA y CLIENTE no dependen de nadie: van primero. PRODUCTO necesita su categoría; PEDIDO necesita su cliente; DETALLE necesita pedido y producto. Ese es el orden de los ejercicios.

Ejercicio 10
Difícil
Tienda online · DELETE en orden
Borrar sin romper la FK

Quieres eliminar el pedido 1, pero tiene líneas de detalle apuntándolo. El orden importa: primero el hijo, luego el padre.

Elimina el pedido 1
  1. Intenta borrar directo el pedido 1 y observa el error.
  2. Hazlo bien: borra primero las líneas de ese pedido, luego el pedido.
Ver solución
-- Falla: hay detalles apuntando al pedido 1
DELETE FROM pedido WHERE id_pedido = 1;
ORA-02292: child record found
-- Orden correcto: primero el hijo, luego el padre
DELETE FROM detalle WHERE id_pedido = 1;
DELETE FROM pedido WHERE id_pedido = 1;
Es el espejo del INSERT: para insertar, primero el padre; para borrar, primero el hijo. (Si vas a seguir con el ejercicio 12, puedes dar ROLLBACK para recuperar el pedido 1.)
Ejercicio 11
Difícil
Tienda online · TCL
Deshacer y luego confirmar

Una venta descuenta stock. Pruébalo, míralo, arrepiéntete con ROLLBACK, y recién cuando estés seguro confirma con COMMIT.

Un día en la tienda
  1. Se venden 2 unidades del producto 1: baja su stock en 2 (stock = stock - 2).
  2. Míralo con un SELECT: el stock bajó.
  3. Arrepiéntete: deshaz el cambio con ROLLBACK y comprueba que volvió.
  4. Ahora la venta va en serio: vuelve a descontar el stock y confirma con COMMIT.
Ver solución
UPDATE producto SET stock = stock - 2 WHERE id_producto = 1;
SELECT * FROM producto WHERE id_producto = 1; -- stock menor
ROLLBACK;
SELECT * FROM producto WHERE id_producto = 1; -- stock original de vuelta
UPDATE producto SET stock = stock - 2 WHERE id_producto = 1;
COMMIT;
El ROLLBACK funciona porque no diste COMMIT entremedio. Tras el COMMIT final, el descuento es definitivo.
