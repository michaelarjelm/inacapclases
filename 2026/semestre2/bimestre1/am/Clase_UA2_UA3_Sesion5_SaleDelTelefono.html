Concepto
Por qué Firebase
Un backend sin backend
Firebase
Una plataforma de Google que da autenticación, base de datos y otros servicios listos para usar desde un SDK, sin tener que programar ni hospedar un servidor propio.

La idea original de este proyecto era conectarse al Atlas (MongoDB) de otro ramo tuyo. Se descartó: Realm/Atlas Device Sync (el puente que hacía posible conectar Android directo a Mongo) llegó a su fin de vida, y la única alternativa era programar y mantener una API propia entre medio.

Firebase resuelve exactamente ese problema: Android se conecta directo con Firestore (su base de datos) y con Firebase Authentication (su login), sin ningún servidor intermedio que ustedes tengan que construir.

ℹ
Por qué un BoM y no versiones sueltas

Firebase tiene muchas librerías (Auth, Firestore, Storage...) que deben usar versiones compatibles entre sí. El BoM ("Bill of Materials") fija todas esas versiones de una vez — así no arriesgan mezclar una versión de Auth con una de Firestore que no se llevan bien.

El código generado
El login, en Kotlin
MainActivity.kt
fun onIngresarClick(view: View) {
    // Busca el campo de usuario (ahora es el email real)
    val edtUsuario = findViewById<EditText>(R.id.edtUsuario)
    // Busca el campo de contrasena
    val edtPassword = findViewById<EditText>(R.id.edtPassword)

    val email = edtUsuario.text.toString()
    val password = edtPassword.text.toString()

    // Le pide a Firebase que valide el email y la contrasena
    FirebaseAuth.getInstance().signInWithEmailAndPassword(email, password)
        .addOnCompleteListener { tarea ->
            if (tarea.isSuccessful) {
                // Credenciales correctas: avanza a Bienvenida
                val intent = Intent(this, BienvenidaActivity::class.java)
                intent.putExtra("usuario", email)
                startActivity(intent)
            } else {
                // Firebase rechazo el login: el email no existe o la clave esta mala
                Toast.makeText(this, "Usuario o contrasena incorrectos", Toast.LENGTH_SHORT).show()
            }
        }
}
Por qué
Incremento 22, una aclaración
Una espera que es real
ℹ
Por qué un addOnCompleteListener y no un if directo

Validar contra Firebase implica ir a internet y volver — no pasa al instante. El addOnCompleteListener le dice a Kotlin "sigue con lo tuyo, y cuando la respuesta llegue, ejecuta este bloque". Es el mismo tipo de espera sin congelar la pantalla que ya vieron con postDelayed en la sesión pasada, pero esta vez la espera es real: depende de la red.

RecyclerView: una lista de verdad
RecyclerView + Adapter + ViewHolder
Un RecyclerView muestra una lista larga sin crear una vista por cada fila de una vez — reutiliza (recicla) las filas que salen de pantalla. El Adapter es el puente entre los datos y las filas; el ViewHolder guarda las referencias a las vistas de una fila, para no buscarlas de nuevo cada vez.

A diferencia del Switch o el Spinner de la sesión pasada, esto son tres piezas nuevas que trabajan juntas — por eso hoy la construimos completa, ya conectada a datos reales, en vez de con una lista simulada como se había pensado en un principio.

Lectura.kt
// Representa un documento guardado en la coleccion "lecturas" de Firestore
data class Lectura(
    // Firestore llena este campo solo con el id real del documento
    @DocumentId val id: String = "",
    // El dato que escribe la dupla
    val descripcion: String = "",
    // Reservado para cuando el sensor real mande un numero (sesion 7 en adelante)
    val valor: Double = 0.0
)
💡
Por qué todos los campos tienen valor por defecto

Firestore necesita poder crear un objeto Lectura "vacío" primero y llenarlo después con los datos del documento. Sin valores por defecto, esa conversión automática falla.

Conectando con la nube
Escuchar la colección en tiempo real
🤖 Prompt para Antigravity
"En la Activity de la lista, crea escucharLecturas(): configura el RecyclerView con un LinearLayoutManager, y agrega un addSnapshotListener a la colección 'lecturas' de Firestore que convierta cada documento en un objeto Lectura y actualice el adapter con la lista más reciente. Comenta cada línea."
ListaActivity.kt
fun escucharLecturas() {
    // Busca la lista por su id
    val recycler = findViewById<RecyclerView>(R.id.recyclerLecturas)
    // Acomoda los items en una columna, uno debajo del otro
    recycler.layoutManager = LinearLayoutManager(this)

    // Se conecta a la coleccion "lecturas" de Firestore, en tiempo real
    Firebase.firestore.collection("lecturas")
        .addSnapshotListener { snapshot, error ->
            // Si algo salio mal, no sigue
            if (error != null || snapshot == null) return@addSnapshotListener

            // Convierte cada documento en un objeto Lectura
            val lista = snapshot.documents.mapNotNull { it.toObject(Lectura::class.java) }
            // Actualiza el adapter con la lista mas reciente
            recycler.adapter = LecturaAdapter(lista)
        }
}
Por qué
Incremento 24, una aclaración
Una lista que se actualiza sola
ℹ
Por qué addSnapshotListener y no leer una sola vez

Un get() trae los datos una vez. addSnapshotListener se queda escuchando: si otra dupla (o ustedes mismos desde otro teléfono) agrega o borra un documento, la lista se actualiza sola, sin recargar la pantalla.

class LecturaAdapter(private val items: List<Lectura>) :
    RecyclerView.Adapter<LecturaAdapter.LecturaViewHolder>() {

    // Guarda las referencias a las vistas de una fila, para no buscarlas de nuevo
    class LecturaViewHolder(view: View) : RecyclerView.ViewHolder(view) {
        val texto: TextView = view.findViewById(R.id.txtItem)
        val botonBorrar: ImageButton = view.findViewById(R.id.btnBorrar)
    }

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): LecturaViewHolder {
        // Infla el layout de una fila (item_lectura.xml)
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.item_lectura, parent, false)
        return LecturaViewHolder(view)
    }

    override fun onBindViewHolder(holder: LecturaViewHolder, position: Int) {
        // Muestra el dato de esta fila
        holder.texto.text = items[position].descripcion
    }

    override fun getItemCount() = items.size
}

fun onAgregarClick(view: View) {

    val edtNuevaLectura = findViewById<EditText>(R.id.edtNuevaLectura)
    val descripcion = edtNuevaLectura.text.toString()

    // No hace nada si el campo esta vacio

    // Lo agrega como un documento nuevo de la coleccion "lecturas"
    Firebase.firestore.collection("lecturas").add(lectura)
        .addOnSuccessListener {
            // Limpia el campo para el siguiente ingreso
            edtNuevaLectura.setText("")
        }
}

Borrar un ítem
🤖 Prompt para Antigravity
"En LecturaAdapter.kt, dentro de onBindViewHolder, agrega un setOnClickListener a holder.botonBorrar que borre ese documento de la coleccion 'lecturas' de Firestore usando su id. Comenta cada línea."
LecturaAdapter.kt
override fun onBindViewHolder(holder: LecturaViewHolder, position: Int) {
    // La lectura que le toca mostrar a esta fila
    val lectura = items[position]

    // Muestra el dato de esta fila
    holder.texto.text = lectura.descripcion

    // Borra el documento al tocar el icono de basurero de esa fila
    holder.botonBorrar.setOnClickListener {
        Firebase.firestore.collection("lecturas").document(lectura.id).delete()
    }
}
ℹ
Por qué lectura.id y no la posición de la fila

La posición en la lista puede cambiar (si se agrega o borra algo antes que esta fila). El id real del documento en Firestore nunca cambia — es la única forma confiable de saber cuál borrar.
