Lo que venían escribiendo sin saberlo
Qué es un contenedor
ViewGroup
Una vista especial que no muestra nada por sí sola — su único trabajo es acomodar a otras vistas adentro. Un View (un Button, un TextView) es hoja; un ViewGroup es contenedor, y puede tener otros ViewGroups adentro.

Desde la sesión 3 escriben app:layout_constraintTop_toBottomOf en cada vista nueva sin que nadie explicara por qué hace falta. Es porque el contenedor de esa pantalla es un ConstraintLayout — y ese tipo de contenedor exige que cada hijo diga con qué se relaciona.

ContenedorCómo acomoda a sus hijosCuándo conviene
ConstraintLayoutCada vista se ancla a otras con restriccionesPantallas donde varias vistas necesitan alinearse con precisión entre sí
LinearLayoutApila a sus hijos en una sola fila o columna, en el orden en que aparecenUn grupo simple, uno debajo del otro, sin calcular restricciones
FrameLayoutSuperpone a sus hijos, uno encima del otroCasos puntuales, como un ícono de carga sobre una imagen

Incremento 12
El código generado
Mostrar/ocultar, en Kotlin
MainActivity.kt
// Recuerda si la contraseña esta visible, vive mientras la pantalla siga abierta
var mostrandoPassword = false

fun onMostrarPasswordClick(view: View) {
    // Busca el campo de contraseña por su id
    val edtPassword = findViewById<EditText>(R.id.edtPassword)

    // Invierte el estado: si estaba oculta, ahora se muestra, y viceversa
    mostrandoPassword = !mostrandoPassword
    if (mostrandoPassword) {
        // Cambia el tipo de entrada para que el texto se vea normal
        edtPassword.inputType = InputType.TYPE_TEXT_VARIATION_VISIBLE_PASSWORD
    } else {
        // Vuelve a ocultar el texto como puntos
        edtPassword.inputType = InputType.TYPE_CLASS_TEXT or InputType.TYPE_TEXT_VARIATION_PASSWORD
    }
}
ℹ
Por qué Vector Asset y no un ícono del sistema

Los íconos del sistema Android (@android:drawable/...) cambian entre versiones y no siempre existen. El Vector Asset queda guardado adentro de su proyecto, así que siempre va a estar disponible.

MainActivity.kt
// Cuenta cuantas veces fallo el login, vive mientras la pantalla siga abierta
var intentosFallidos = 0

fun onIngresarClick(view: View) {
    // Busca el campo de usuario por su id
    val edtUsuario = findViewById<EditText>(R.id.edtUsuario)
    // Busca el campo de contraseña por su id
    val edtPassword = findViewById<EditText>(R.id.edtPassword)

    // Lee el texto escrito en cada campo
    val usuario = edtUsuario.text.toString()
    val password = edtPassword.text.toString()

    if (usuario.isEmpty() || password.isEmpty()) {
        // Suma un intento fallido
        intentosFallidos++
        // Avisa cuantos intentos van
        Toast.makeText(this, "Completa usuario y contraseña (intento $intentosFallidos)", Toast.LENGTH_SHORT).show()
    }
}

MainActivity.kt
// Revisa que el usuario tenga formato de email valido
if (!android.util.Patterns.EMAIL_ADDRESS.matcher(usuario).matches()) {
    // Muestra el error directo en el campo de usuario
    edtUsuario.error = "Ingresa un email válido"
    // Corta la ejecucion, no sigue validando el resto
    return
}
// Revisa que la contraseña tenga al menos 6 caracteres
if (password.length < 6) {
    // Muestra el error directo en el campo de contraseña
    edtPassword.error = "La contraseña debe tener al menos 6 caracteres"
    return
}
ℹ
Por qué .error y no un Toast

El Toast genérico obligaba a adivinar cuál campo estaba mal. Con .error, Android dibuja un ícono rojo y el mensaje directo sobre el campo que falló — el usuario ve el problema sin tener que pensar.

Incremento 19
El código generado
La barra, en Kotlin
PreferenciasActivity.kt
fun onGuardarPreferenciaClick(view: View) {
    // Busca la barra de progreso por su id
    val pbGuardando = findViewById<ProgressBar>(R.id.pbGuardando)
    // Busca cual RadioButton esta marcado
    val rbCelsius = findViewById<RadioButton>(R.id.rbCelsius)

    // Hace visible la barra de progreso
    pbGuardando.visibility = View.VISIBLE

    // Espera 1 segundo antes de seguir, sin congelar la pantalla mientras tanto
    Handler(Looper.getMainLooper()).postDelayed({
        // Vuelve a ocultar la barra de progreso
        pbGuardando.visibility = View.GONE
        // Calcula que unidad quedo elegida
        val unidad = if (rbCelsius.isChecked) "Celsius" else "Fahrenheit"
        // Confirma el guardado
        Toast.makeText(this, "Guardado: temperatura en $unidad", Toast.LENGTH_SHORT).show()
    }, 1000)
}
ℹ
Por qué postDelayed y no un simple "esperar"

Kotlin no tiene un comando que "congele" la pantalla 1 segundo sin trabarla. postDelayed le dice al sistema "ejecuta esto en 1000 milisegundos", y mientras tanto la app sigue respondiendo con normalidad. Es un adelanto chico de lo asíncrono, sin entrar en el tema todavía.

}
ℹ
finish() vs finishAffinity()

finish() cierra solo la pantalla actual y vuelve a la anterior (Bienvenida). finishAffinity() cierra TODAS las pantallas hasta el login — lo correcto para "cerrar sesión", porque no quieres que con el botón Atrás vuelvan a Bienvenida o Preferencias sin haber iniciado sesión de nuevo.
