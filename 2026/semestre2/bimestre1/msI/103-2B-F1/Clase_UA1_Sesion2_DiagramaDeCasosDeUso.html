¿Qué es
UML?

La palabra que le da nombre a esta unidad. Antes de dibujar nada, hay que saber qué es y para qué sirve.

Definición
La base de toda la unidad
Lenguaje
Unificado de
Modelado
UML · Unified Modeling Language
Un lenguaje visual estándar para representar el diseño de un sistema mediante diagramas normalizados: cualquier persona del área los lee igual, sin importar quién los dibujó.
No es un lenguaje de programación. No se "ejecuta": se dibuja, y sirve para pensar y comunicar el diseño antes de escribir una sola línea de código.

UML no es un solo diagrama, es una familia de diagramas, cada uno pensado para mostrar un aspecto distinto del sistema. Algunos muestran estructura (qué partes tiene el sistema), otros muestran comportamiento (qué hace el sistema paso a paso).

●

El diagrama de casos de uso. Los demás (de base de datos, de flujo, de clases, de componentes, de secuencia) los vas a ir viendo uno por uno en las próximas sesiones, cada uno cuando corresponda. No necesitas conocerlos todos hoy.

Actor y

El primer diagrama de UML que vas a dibujar. Muestra qué puede hacer cada quién con el sistema, sin explicar cómo funciona por dentro.

Definición
El diagrama de hoy
Diagrama de
casos de uso
Diagrama de casos de uso
Un diagrama UML que muestra qué puede hacer un usuario con el sistema, sin explicar cómo lo hace por dentro.
Responde la pregunta "¿qué se puede hacer aquí?", no "¿cómo está programado por dentro?". Eso último lo vas a ver en otra unidad.
Actor
Una persona o sistema externo que interactúa con el sistema. Se dibuja como una figura de palitos, fuera del sistema.
Caso de uso
Una acción concreta que el actor puede realizar con el sistema. Se dibuja como un óvalo, con un verbo en infinitivo adentro, dentro del sistema.
●
De dónde salen los actores y los casos de uso

De tu propio correo. Cada persona que mencionas y cada requerimiento funcional que identifiques ahí es material directo para este diagrama.

Bloque 03
03 · Concepto + demo · 20 min
Include
y extend

No todos los casos de uso se conectan directo a un actor. Algunos dependen de otro caso de uso.

Definición
Dos relaciones entre casos de uso
Siempre ocurre
vs a veces ocurre
Include

Un caso de uso que SIEMPRE ocurre como parte de otro. No es opcional: cada vez que pasa el primero, pasa también el incluido.

Se dibuja con una flecha punteada, apuntando desde el caso de uso base hacia el caso de uso incluido, con la etiqueta <<include>>.

Extend

Un caso de uso que ocurre SOLO A VECES, como una extensión opcional de otro. Depende de una condición.

Se dibuja con una flecha punteada, apuntando desde la extensión hacia el caso de uso base, con la etiqueta <<extend>>.

En el tallerRelaciónPor qué
Generar orden de trabajo → Validar patenteIncludeToda orden de trabajo necesita una patente válida. Nunca se salta este paso.
Cotizar repuesto importado → Generar orden de trabajoExtendSolo pasa si la orden incluye un repuesto importado. La mayoría de las veces no aplica.
●
La pregunta para decidir cuál usar

"¿Esto pasa siempre, o solo a veces?" Si la respuesta es siempre, es include. Si depende de una condición, es extend.

Diagrama de casos de uso · paso 5 de 6
Elemento agregado: relación include
Función: conecta un caso de uso base con otro que ocurre siempre como parte de él. Flecha punteada, apuntando hacia el caso incluido.
Ejemplo en este diagrama: "Generar orden de trabajo" incluye "Validar patente": toda orden necesita una patente válida, sin excepción.
Construcción · 6 de 6
El último elemento: una relación que depende de una condición
Aquí aparece
el extend, diagrama completo
Diagrama de casos de uso · Sistema del taller (completo)
Elemento agregado: relación extend
Función: conecta una extensión opcional con el caso de uso base. Flecha punteada, apuntando desde la extensión hacia el caso base.
Ejemplo en este diagrama: "Cotizar repuesto importado" extiende "Generar orden de trabajo": solo pasa si la orden incluye un repuesto importado, la mayoría de las veces no aplica.
