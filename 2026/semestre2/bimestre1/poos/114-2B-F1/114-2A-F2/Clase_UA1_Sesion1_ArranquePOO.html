El caso
El sistema que vamos a construir juntos
Un taller
mecánico

Un taller mecánico lleva sus órdenes de trabajo en un cuaderno y quiere un sistema real. Esto es lo que pidió, tal como lo contó:

1
Autos, motos y camiones, cada uno a su tarifa
Cobra la mano de obra distinto según el tipo de vehículo, sin preguntar "de qué tipo eres" en cada parte del código. Vas a aprender: herencia y polimorfismo.
2
Mecánicos y recepcionistas no hacen lo mismo
Cada uno necesita ver y poder hacer cosas distintas en el sistema. Vas a aprender: tipos de usuario y permisos, con contraseñas hasheadas.
3
Ninguna patente ni RUT inválido
Si algo está mal escrito, el sistema lo rechaza ahí mismo, no lo deja pasar. Vas a aprender: encapsulamiento y validación.
4
Cada orden lleva varios repuestos, con su cantidad y precio
No es un repuesto suelto: es una lista dentro de la orden. Vas a aprender: una transacción con líneas de detalle.
5
Dos reglas que nunca se pueden romper
No se entrega un vehículo que nunca ingresó al taller, ni se usa un repuesto sin stock. Vas a aprender: excepciones propias.
6
El dólar del repuesto importado, actualizado
Varios repuestos son importados: el precio en pesos cambia todos los días según el valor del dólar de hoy. Vas a aprender: consumo de una API externa.
7
Nada se puede perder al cerrar el programa
Hoy todo vive en un cuaderno de papel; el dueño quiere que sobreviva aunque se apague el computador. Vas a aprender: base de datos y CRUD.

Este es el caso con el que vamos a trabajar en clases. Todo lo que veamos se va a construir sobre él, sesión a sesión, hasta tener el sistema completo.

Herencia, polimorfismo, CRUD, hash, excepciones. Ninguna se supone que la sepas hoy: esa es la lista del temario del bimestre. Cada una tiene su sesión y se explica desde cero cuando llegue.

02 · Concepto · 25 min
¿Por qué existen
los objetos?

No vamos a empezar con la definición. Vamos a escribir el mismo programa de dos formas y a ver cuál se rompe primero.

Definición
Dos palabras antes de ver código
Estado y regla
de negocio
El estado de un programa
Todos los datos que el programa tiene guardados en un momento dado.
En el taller: qué vehículos hay, cuáles están adentro y cuáles ya se entregaron. Si el estado se corrompe, el programa empieza a mentir.
Una regla de negocio
Una condición que el negocio real exige y que el programa tiene que respetar siempre.
"No se puede entregar un vehículo que nunca ingresó al taller." No es una regla de programación: es una regla del taller.
●
Por qué importan estas dos

Toda la comparación que viene ahora se trata de una sola pregunta: ¿dónde vive el estado y quién se hace cargo de que las reglas se cumplan?

Demostración
Versión 1
El taller
como siempre
taller_v1.py · procedural
# Todo el estado vive suelto, en una lista global
vehiculos = []

def ingresar(patente, modelo, tipo):
    vehiculos.append({"patente": patente, "modelo": modelo,
                      "tipo": tipo, "en_taller": True})

def entregar(patente):
    for v in vehiculos:
        if v["patente"] == patente and v["en_taller"]:
            v["en_taller"] = False
            return True
    return False

def calcular_mano_obra(patente, horas):
    for v in vehiculos:
        if v["patente"] == patente:
            if v["tipo"] == "auto":   return horas * 25000
            if v["tipo"] == "moto":   return horas * 15000
            if v["tipo"] == "camion": return horas * 40000
    return 0
●
Esto es Python como ya lo conoces

Una lista, diccionarios y tres funciones. Nada nuevo todavía. El estado del programa es esa lista vehiculos, y la regla de negocio está dentro de entregar.

Funciona. Y sin embargo, en tres meses este archivo es un problema.

El cliente llama y dice: "ahora también atendemos buses".
Anoten en el cuaderno: ¿qué partes de este código hay que tocar? Cuenten cuántos lugares. Después lo vemos juntos.
Demostración
Qué se rompe
El cliente pide
un cambio

"Ahora también atendemos buses, y el cliente con deuda no puede dejar su vehículo."

Lo que tienes que tocar
  • Otro if en calcular_mano_obra
  • Otro if en cada función que revise el tipo
  • Buscar todos los lugares donde se lee v["tipo"]
Lo que nadie te avisa
  • Si escribes v["en_talier"], Python no reclama hasta que explota
  • Cualquier parte del programa puede cambiar en_taller sin pasar por entregar
  • La regla de negocio quedó repartida en varias funciones
●
El problema de fondo

Los datos están por un lado y el comportamiento por otro. Nada obliga a que un vehículo se entregue solo a través de entregar().

Demostración
Versión 2
El mismo taller
con objetos
taller_v2.py · orientado a objetos
class Vehiculo:
    def __init__(self, patente, modelo):
        self.patente = patente
        self.modelo  = modelo
        self._en_taller = False     # nadie lo toca desde afuera

    def ingresar(self):
        self._en_taller = True

    def entregar(self):
        if not self._en_taller:
            raise VehiculoNoIngresadoError(self.patente)
        self._en_taller = False

    def tarifa_hora(self):
        raise NotImplementedError


class Auto(Vehiculo):
    def tarifa_hora(self): return 25000

class Camion(Vehiculo):
    def tarifa_hora(self): return 40000

Agregar buses ahora es una clase nueva de dos líneas. Ningún if existente se toca.

Guía
Todo lo que acabas de ver por primera vez
Cómo se lee
ese código

Aparecieron seis cosas nuevas. Hoy solo necesitas reconocerlas; cada una tiene su sesión más adelante.

class Vehiculo:
Declara un molde nuevo llamado Vehiculo. Todo lo que va indentado debajo le pertenece.
__init__
Un método especial que se ejecuta solo, en el momento en que se crea el objeto. Sirve para dejarle sus datos iniciales. En la próxima sesión lo vemos en detalle.
self
La palabra con la que el objeto se refiere a sí mismo. self.patente es "la patente de este vehículo", no la de otro.
_en_taller
El guion bajo del principio es una señal para el equipo: "este dato es interno, no lo toques desde afuera".
class Auto(Vehiculo):
El paréntesis significa que Auto hereda de Vehiculo: recibe gratis todo lo que el padre ya tenía.
raise
Avisa que ocurrió un error y detiene la operación. Es la forma de hacer cumplir una regla de negocio. El nombre VehiculoNoIngresadoError es un error que inventamos nosotros para este dominio. Todo esto se ve completo en la sesión 8.
●
Si algo de esto no te quedó claro, está bien

Hoy la meta es entender por qué conviene escribir así, no memorizar la sintaxis. La próxima sesión empezamos por atributos y métodos, desde cero.

Definición
Antes de ponerle nombre al estilo
¿Qué es un
objeto?
Objeto
Una unidad que junta datos y comportamiento: sabe cosas de sí misma y sabe hacer cosas con esas cosas que sabe.
En taller_v2.py, cada vehículo que crean con Auto(...) es un objeto: sabe su patente y su modelo, y sabe ingresar y entregarse. En la versión 1 eso mismo vivía repartido en un diccionario y tres funciones sueltas.

Por eso el programa de la versión 2 se organiza distinto: en vez de preguntar ¿qué pasos hay que ejecutar?, cada objeto responde por sus propios datos y sus propias reglas.

●
Todavía no es toda la palabra

Objeto es una de cuatro palabras que van a necesitar (clase, objeto, atributo, método). Las otras tres llegan más adelante, hoy mismo, en el bloque de vocabulario.

03 · Concepto · 10 min
Qué es la
programación
orientada a objetos

Ya vieron las dos formas de escribir el mismo programa. Ahora, cómo se llama cada una y por qué.

Definición
Empecemos por la palabra grande
¿Qué es un
paradigma?
Paradigma de programación
Una forma de organizar el código. No es un lenguaje: es una manera de pensar cómo se arma el programa.
Python permite varias. El mismo lenguaje, dos formas distintas de escribir lo mismo: exactamente lo que acaban de ver.
Paradigma procedural

El programa es una secuencia de instrucciones y funciones que operan sobre datos sueltos.

La pregunta que uno se hace al programar: ¿qué pasos hay que ejecutar?

Es la versión 1 del taller.

Paradigma orientado a objetos

El programa es un conjunto de objetos que guardan sus propios datos y saben hacer cosas con ellos.

La pregunta que uno se hace: ¿qué cosas existen en este problema y qué sabe hacer cada una?

Es la versión 2.

●
Ninguno es "el correcto"

El procedural sirve perfecto para un script de veinte líneas. La orientación a objetos gana cuando el programa crece y hay que seguir cambiándolo, que es justo lo que vieron recién.

Definición
El nombre de esta asignatura
Programación
orientada a objetos
Programación orientada a objetos · POO
El paradigma que organiza el programa en objetos: unidades que juntan datos y comportamiento, y que representan cosas del problema que se está resolviendo.
En inglés se abrevia OOP, de object oriented programming.

Por qué se llama "orientada a". Porque el programa entero se orienta, se organiza, alrededor de esos objetos. En el procedural el centro son las funciones y los datos andan sueltos. Aquí el centro son los objetos, y cada uno se hace cargo de lo suyo.

Clase
class Auto:
El molde. Define qué datos y qué acciones va a tener cada auto. No es un auto: es la definición de lo que es ser un auto.
Objeto
v = Auto("KXPR84", "Yaris 2019")
Un ejemplar concreto hecho con ese molde. De una clase salen miles de objetos, cada uno con sus propios valores.
Atributo
self.patente
Un dato que el objeto guarda. Es lo que el objeto sabe de sí mismo.
Método
def entregar(self):
Una acción que el objeto puede realizar. Es lo que el objeto hace.
