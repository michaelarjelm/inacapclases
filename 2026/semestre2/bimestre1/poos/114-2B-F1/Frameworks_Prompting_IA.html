Frameworks
de prompting

Desde la sesión 6 le vienen escribiendo prompts a agy, cada vez con más autonomía. Esto no es materia nueva ni se evalúa en ninguna prueba: son ocho formas de estructurar un prompt para que la respuesta que reciben sea la que necesitan, a la primera. Léanlo cuando les convenga, a su propio ritmo.

Antes de los ocho frameworks
Un prompt vago
da una respuesta vaga

"Hazme la clase Vehiculo" y "Agregale a Vehiculo un constructor que reciba patente y anio, con patente validada como property" no le piden lo mismo a agy, aunque ustedes tengan la misma idea en la cabeza. La diferencia entre ambos prompts es exactamente lo que cada framework de esta lámina ordena.

Idea central
Ninguno es "el correcto"
Ocho moldes
para la misma idea

Un framework de prompting es una lista corta de partes que conviene incluir, en un orden que ayuda a no olvidar ninguna. No son reglas de sintaxis que Python revise: son una checklist para ustedes mismos, antes de apretar enter.

●
No hay que memorizarlos los ocho

Con RTF y CARE ya cubren la mayoría de lo que van a pedir en este módulo. Los otros seis sirven para situaciones más específicas -- revisen la tabla comparativa del cierre cuando no sepan cuál usar.

●
Estas ocho combinaciones de letras no son un estándar oficial

Circulan así en varios lugares de internet, con distintas variantes según el autor. Las definiciones de esta lámina siguen una fuente consistente: vhtc.org, "ChatGPT Prompt Frameworks Reference". Lo que importa no es memorizar la sigla exacta, es la costumbre de pensar en partes antes de escribir.

01
Para pedidos simples y directos
RTF

Role · Task · Format. El más corto de los ocho, y el que más van a usar sin darse cuenta.

Definición
Tres partes, un prompt de una línea
¿Qué es
RTF?
R
Role
Qué rol o experiencia le piden a agy que asuma
T
Task
Qué tiene que hacer, en concreto
F
Format
Cómo tiene que entregar el resultado
Cuándo usarlo
Instrucciones directas, sin ambigüedad posible sobre lo que quieren.
Es exactamente el patrón que ya usaron en S7 y S8: "Creá tres archivos... con class NombreClase(Vehiculo)... Dejalas vacías con pass" -- sin saberlo, ya estaban aplicando RTF.
Ejemplo
Sobre el taller mecánico
Con y sin
estructura
Prompt vago
"hazme el metodo entregar"
Con RTF
[Role] "Sos un desarrollador Python que sigue el estilo del resto del archivo." [Task] "Agregale a Vehiculo el método entregar(): marca en_taller en False solo si estaba en True antes." [Format] "Entregalo con un comentario en español en cada línea, mismo estilo que ingresar()."
●
La diferencia no es cortesía, es información

El segundo prompt le da a agy tres datos que el primero no tiene: qué estilo de código mantener, la regla de negocio exacta, y cómo comentar. El primero deja que agy adivine los tres.

02
Para decisiones de diseño
SOLVE

Situation · Objective · Limitations · Vision · Execution. Cuando el pedido no es "escribime este método", es "ayudame a decidir cómo resolver esto".

Definición
Cinco partes, pensado para problemas más grandes
¿Qué es
SOLVE?
S
Situation
El contexto o punto de partida
O
Objective
Qué quieren lograr
L
Limitations
Qué restricciones no se pueden cruzar
V
Vision
Cómo se ve el resultado final
E
Execution
Los pasos concretos para llegar
Cuándo usarlo
Tareas de pensamiento estratégico, no solo de escribir código.
Ejemplo
Sobre el taller mecánico
Decidir cómo
proteger a Vehiculo
Con SOLVE
[Situation] "Tengo Vehiculo con tres hijas (Auto, Moto, Camion), cada una cobra distinto." [Objective] "Quiero que nunca se pueda crear un Vehiculo genérico, solo sus hijas." [Limitations] "No puedo tocar el constructor de Auto, Moto ni Camion." [Vision] "Que crear un Vehiculo solo tire un error apenas se intente." [Execution] "Dame los pasos concretos para lograrlo con abc."
●
No pide código todavía, pide un plan

SOLVE está pensado para la conversación de "cómo lo resuelvo", antes de pedir el código en sí. Es el mismo tipo de razonamiento que llevó a decidir ABC en la sesión 8.

03
Para tareas chicas del día a día
TAG

Task · Action · Goal. Tres palabras, para no perder tiempo en pedidos cortos.

Definición
Parecido a RTF, con el foco en el objetivo
¿Qué es
TAG?
T
Task
Qué hay que hacer
A
Action
El paso específico a tomar
G
Goal
Qué están tratando de lograr con eso
Cuándo usarlo
Cambios incrementales chicos, del tipo que hicieron en las actividades de S7 y S8.
Ejemplo
Sobre el taller mecánico
Agregar un dato
a Camion
Con TAG
[Task] "Camion necesita guardar su capacidad de carga." [Action] "Agregale un atributo capacidad_carga, con su propio __init__ que llame a super()." [Goal] "Que Camion siga funcionando igual que antes, con ese dato nuevo disponible."
●
El Goal evita que agy se pase de largo

Sin la G, agy podría "mejorar" cosas que no pediste. Con el objetivo explícito ("que siga funcionando igual"), sabe cuál es el límite del cambio.

04
Para redactar contenido o documentación
RACE

Role · Action · Context · Expectation. No es solo para código: sirve para pedir textos.

Definición
Pensado para que el tono también quede claro
¿Qué es
RACE?
R
Role
La perspectiva que debe asumir
A
Action
La tarea u objetivo concreto
C
Context
El trasfondo o situación relevante
E
Expectation
El resultado que quieren ver
Cuándo usarlo
Escribir contenido, no solo código: documentación, mensajes, explicaciones para otros.
Ejemplo
Sobre el taller mecánico
Documentar
el repo
Con RACE
[Role] "Sos un redactor técnico que escribe documentación clara para principiantes." [Action] "Escribime un README.md breve para el repo Taller-Mecanico." [Context] "Es un proyecto educativo de POO en Python, con Vehiculo, Auto, Moto y Camion." [Expectation] "Tres párrafos, sin jerga innecesaria, para que un alumno nuevo entienda de qué se trata."
●
El Role cambia el resultado más de lo que parece

El mismo pedido sin el Role probablemente devuelva un README lleno de jerga técnica. Pedirle explícitamente "para principiantes" cambia el vocabulario que usa.

05
Para investigar y comparar opciones
DREAM

Define · Research · Execute · Analyse · Measure. Convierte a agy en asistente de investigación.

Definición
Cinco partes, para trabajo analítico
¿Qué es
DREAM?
D
Define
Aclarar el problema o la pregunta
R
Research
Pedir trasfondo o evidencia de apoyo
E
Execute
Pedir un plan o solución concreta
A
Analyse
Pedir que interprete o razone sobre eso
M
Measure
Definir cómo se mide si funcionó
Cuándo usarlo
Comparar alternativas antes de decidir, con el "por qué" incluido.
Ejemplo
Sobre el taller mecánico
NotImplementedError
o ABC
Con DREAM
[Define] "Necesito decidir cómo evitar que Vehiculo se instancie solo." [Research] "Dame las ventajas y desventajas de NotImplementedError contra ABC + @abstractmethod." [Execute] "Proponeme cuál conviene para este caso." [Analyse] "Explicame por qué esa es la mejor opción para un vehículo que nunca debería existir solo." [Measure] "Decime cómo confirmo que quedó bien implementado."
●
Es la tabla comparativa de S8, convertida en prompt

El bloque de "NotImplementedError contra ABC" que vieron en la sesión 8 es exactamente el tipo de respuesta que produce un DREAM bien armado.

06
Para resolver un problema con límites claros
PACT

Problem · Approach · Compromise · Test. Para cuando algo salió mal y hay que arreglarlo.

Definición
Cuatro partes, orientado a debugging y decisiones
¿Qué es
PACT?
P
Problem
El problema, dicho con claridad
A
Approach
El método o estrategia a seguir
C
Compromise
Qué límites o restricciones hay que respetar
T
Test
Cómo van a confirmar que quedó resuelto
Cuándo usarlo
Errores, conflictos, o decisiones donde hay algo que no se puede perder en el camino.
Ejemplo
Sobre el taller mecánico
Un conflicto
de git
Con PACT
[Problem] "Al hacer merge me aparece un conflicto en vehiculo.py." [Approach] "Explicame qué pasó y qué opciones tengo para resolverlo." [Compromise] "No quiero perder ninguno de los dos cambios si es posible conservarlos." [Test] "Decime cómo confirmo que quedó bien resuelto después."
●
El Compromise es la parte que más se olvida

Sin decir explícitamente qué no puede perderse, agy puede "resolver" el conflicto descartando el cambio equivocado. Esa restricción es la que evita el error.

07
Para instrucciones paso a paso
RISE

Role · Input · Steps · Expectation. Cuando quieren que les enseñe algo, no que lo haga por ustedes.

Definición
Cuatro partes, pensado para aprender haciendo
¿Qué es
RISE?
R
Role
Qué persona debe adoptar (instructor, guía)
I
Input
Qué datos o contexto ya tienen
S
Steps
Que pida instrucciones en secuencia
E
Expectation
Cómo debe quedar el resultado final
Cuándo usarlo
Aprender un proceso nuevo (como git), no solo obtener el resultado final.
Ejemplo
Sobre el taller mecánico
Entender el
flujo de git
Con RISE
[Role] "Sos un instructor de git para alguien que recién empieza." [Input] "Tengo mi repo clonado, con la rama desarrollo ya creada." [Steps] "Explicame paso a paso cómo hacer commit y push de mi rama." [Expectation] "Una lista numerada de comandos, cada uno con qué hace y por qué."
●
La diferencia con TAG: acá quieren entender, no solo terminar

Si solo necesitaran que el commit se hiciera, TAG alcanza. RISE se usa cuando el objetivo es que la próxima vez lo hagan solos, sin preguntar.

08
Para que les explique con un ejemplo real
CARE

Context · Action · Result · Example. El que más reduce que agy invente algo que no pasa de verdad.

Definición
Cuatro partes, con un ejemplo concreto obligatorio
¿Qué es
CARE?
C
Context
El trasfondo o situación
A
Action
Qué pasos se dieron o qué se pide
R
Result
Qué resultado se busca o se obtuvo
E
Example
Un caso o dato de apoyo, concreto
Cuándo usarlo
Cuando necesitan que la respuesta esté anclada a algo real, no a una explicación genérica.
Ejemplo
Sobre el taller mecánico
Por qué Auto
no necesita __init__
Con CARE
[Context] "En el taller mecánico, Auto hereda de Vehiculo y nunca definió su propio __init__." [Action] "Explicame por qué Auto puede instanciarse igual, con patente y anio." [Result] "Quiero entender qué pasa por dentro cuando lo instancio, no solo que funciona." [Example] "Usá el caso real de Auto('AB1234', 2018) para mostrarlo paso a paso."
●
El Example es lo que evita una respuesta genérica de manual

Sin él, la respuesta puede quedarse en "Python busca el método en la clase padre" en abstracto. Con un caso real (Auto("AB1234", 2018)), la explicación tiene que seguir ese objeto específico paso a paso.

Antes de escribir el prompt, pregúntense: ¿agy sabe qué rol cumplir, qué tiene que hacer exactamente, y cómo se ve un buen resultado? Si las tres respuestas están en su prompt, ya están usando alguno de estos ocho, se llame como se llame.
