Bloque 01
01 · Concepto · 14 min
Duck
typing

Otra forma de mirar el polimorfismo que ya usaron ayer con tarifa_hora().

Definición
Si camina como pato y grazna como pato
¿Qué es
duck typing?
Duck typing
La idea de que a Python no le importa de qué clase es un objeto, sino si tiene el método o el atributo que se necesita usar en ese momento.
El nombre viene del dicho en inglés: "si camina como pato y grazna como pato, entonces es un pato". No hace falta que algo sea oficialmente de una clase para tratarlo como tal, basta con que tenga el método que hace falta usar.
duck_typing.py · archivo de práctica, aparte del modelo real
class Repuesto:
    def resumen(self):
        return "Filtro de aceite, stock: 12"

class Cliente:
    def resumen(self):
        return "Juan Perez, sin deuda"

def mostrar(objeto):
    print(objeto.resumen())

mostrar(Repuesto())
mostrar(Cliente())
●
Repuesto y Cliente no tienen ninguna relación de herencia

Ninguna es hija de la otra, ni comparten un padre común -- de hecho, en su diagrama completo tampoco tienen ninguna relación entre sí. Y aun así, mostrar() funciona con las dos, porque a Python solo le importa que el objeto que reciba tenga un método resumen(). Eso es duck typing: el polimorfismo no depende de que exista una jerarquía de herencia.

●
La diferencia con lo que vieron ayer

Ahí el polimorfismo funcionaba porque Auto, Moto y Camion heredaban de Vehiculo y sobrescribían tarifa_hora(). Acá funciona sin ninguna herencia de por medio. Las dos son formas válidas de la misma idea: mismo mensaje, cada objeto responde a su manera.

Por qué existe
El problema que resuelve, no solo la sintaxis
¿Por qué existe
el duck typing?

A veces dos clases necesitan comportarse igual frente a un mismo mensaje, pero forzarlas a compartir un padre común no tiene sentido de negocio (Repuesto y Cliente no "son un" tipo de nada en común), o directamente no se puede: si la clase viene de una librería externa, no pueden agregarle un padre. Duck typing resuelve exactamente ese caso: pedir el mismo comportamiento sin exigir el mismo árbol genealógico.

●
En el mundo corporativo

Python entero está construido así: cualquier objeto con un método __iter__ funciona en un for, sin heredar de nada especial. En testing, un "mock" (un objeto falso que se usa para probar código sin conectarse a servicios reales) funciona porque responde a los mismos métodos que el objeto real, no porque comparta su clase. Librerías como pandas o NumPy dependen de esto: código que procesa "algo que tenga .shape y se pueda indexar" funciona con muchos tipos de datos distintos sin que ninguno herede del otro.

Definición
Prohibir la instanciación directamente
¿Qué es una
clase abstracta?
Clase abstracta
Una clase que no se puede instanciar directamente. Solo sirve como padre para que otras clases hereden de ella. Si alguien intenta crear un objeto de la clase abstracta misma, Python lo rechaza altiro.
En Python se construye con el módulo abc: la clase hereda de ABC, y los métodos que las hijas deben completar se marcan con @abstractmethod.
vehiculo.py · ahora abstracta (idea general)
from abc import ABC, abstractmethod

class Vehiculo(ABC):
    def __init__(self, patente, anio):
        self.patente = patente  # ... resto del constructor, sin cambios

    @abstractmethod
    def tarifa_hora(self):
        pass
python3
>>> v = Vehiculo("AB1234", 2018)
TypeError: Can't instantiate abstract class Vehiculo
with abstract method tarifa_hora

>>> a = Auto("AB1234", 2018)
# funciona: Auto ya tiene su propio tarifa_hora() desde ayer

●
Para su clase padre principal, usen ABC

Si su modelo tiene una clase que nunca debería existir por sí sola, siempre de un subtipo, ABC lo garantiza. Es más seguro que confiar en que nadie la instancie por error, sea que su placeholder actual devuelva un valor genérico o lance NotImplementedError.

Por qué existe
El problema que resuelve, no solo la sintaxis
¿Por qué existe
ABC?

El problema no es solo "alguien podría instanciar Vehiculo por error hoy": es que en un equipo grande, meses después, alguien que nunca vio esta conversación puede hacerlo sin saber que está mal. Confiar en que "todos se van a acordar de no hacerlo" no escala. ABC mueve esa regla del acuerdo verbal del equipo a algo que el propio lenguaje hace cumplir, sin depender de que nadie se acuerde.

●
En el mundo corporativo

Los frameworks grandes están llenos de clases abstractas para forzar contratos: en Django, la clase base de un comando de administración (BaseCommand) exige que cada comando implemente handle(), o directamente no arranca. En Django REST Framework, una clase de permisos personalizada debe implementar has_permission() porque la clase base es abstracta. Cuando muchas personas contribuyen al mismo código a lo largo de años, esta clase de contratos explícitos evita errores que un simple acuerdo de equipo ("acordate de implementar este método") no puede garantizar.

from abc import ABC, abstractmethod

class Vehiculo(ABC):
    def __init__(self, patente, anio):
        self.patente = patente
        self.__anio = anio
        self.__en_taller = False

    @property
    def patente(self):
        return self.__patente

    @patente.setter
    def patente(self, valor):
        if len(valor) < 6 or " " in valor:
            raise ValueError(f"Patente inválida: {valor!r}")
        self.__patente = valor

    # ... property en_taller, ingresar(), entregar(): sin cambios

    @abstractmethod
    def tarifa_hora(self):
        pass  # ya no retorna 5000: cada hija esta obligada a completarlo

Bloque 03
03 · Concepto · 10 min
Qué pasa
cuando nadie
atrapa el error

Antes de aprender a manejarlo, hay que saber leer lo que Python muestra cuando no se maneja.

Definición
El mensaje que ya han visto varias veces
¿Qué es un
traceback?
Traceback
El reporte que Python muestra cuando una excepción no fue manejada: en qué archivo y en qué línea ocurrió, y la cadena de llamadas que lo llevó hasta ahí.
No es un error del traceback en sí: es Python contándote exactamente dónde se rompió todo.
terminal
$ python3 probar_patente.py
Traceback (most recent call last):
  File "probar_patente.py", line 3, in <module>
    v = Auto("KX12", 2018)
  File "vehiculo.py", line 12, in patente
    raise ValueError(f"Patente inválida: {valor!r}")
ValueError: Patente inválida: 'KX12'
ParteQué dice
La última líneaEl tipo de excepción y el mensaje. Es lo primero que hay que leer, no lo último.
Las líneas de arribaEl camino que siguió el programa: qué archivo llamó a qué, hasta llegar al error.
●
Léanlo de abajo hacia arriba

La costumbre es leer de arriba a abajo, pero un traceback se lee al revés: primero la última línea, que dice qué pasó. Después, si hace falta, subes para ver cómo se llegó hasta ahí.

●
Este ValueError ya lo conocen

Es el mismo que armaron ayer en el setter de patente. La diferencia de hoy es que hasta ahora dejaban que reventara el programa entero: eso es exactamente lo que try/except va a evitar.

Bloque 04
04 · Concepto · 18 min
try /
except

Decirle al programa: intenta esto, y si sale mal, no te caigas.

Definición
Los dos bloques mínimos
¿Qué son
try y except?
try
Un bloque que dice "intenta ejecutar este código". Si algo dentro de él lanza una excepción, Python deja de ejecutar esa parte y busca un except que la maneje.
except
El bloque que se ejecuta solo si ocurrió la excepción que indica. Es donde decides qué hacer en vez de dejar que el programa se caiga.
probar_patente.py
try:
    v = Auto("KX12", 2018)
except ValueError as error:
    print("No se pudo crear el vehiculo:", error)
    v = None

print("El programa sigue funcionando")
salida
$ python3 probar_patente.py
No se pudo crear el vehiculo: Patente inválida: 'KX12'
El programa sigue funcionando
●
La diferencia con el bloque anterior

El mismo error ocurrió. Pero esta vez el programa no se detuvo: imprimió un mensaje entendible y siguió. as error guarda la excepción en una variable para poder usar su mensaje.

Por qué existe
El problema que resuelve, no solo la sintaxis
¿Por qué existe
try/except?

Sin manejo de excepciones, un solo dato mal formado en cualquier parte del programa tumba TODO el programa, aunque el resto no tuviera nada que ver con ese error. La alternativa (revisar "a mano" con if cada cosa que podría salir mal, antes de que pase) es imposible de mantener: hay demasiados casos, y muchos ni se les ocurren hasta que pasan de verdad. try/except separa el código que puede fallar del código que decide qué hacer si falla, sin que uno tumbe al otro.

●
En el mundo corporativo

Un checkout de e-commerce que procesa el pago de una tarjeta rechazada no puede crashear la página entera: atrapa el error y muestra "tarjeta rechazada, intenta con otra". Las APIs bien diseñadas atrapan errores internos y devuelven una respuesta clara (código 400, 404, 500 con un mensaje) en vez de que el servidor completo se caiga. Las llamadas a servicios externos (una pasarela de pago, un banco, otro servidor) casi siempre van envueltas en try/except con reintentos, porque una caída de red momentánea no debería significar perder la venta.

Bloque 05
05 · Concepto · 14 min
finally
y varios
except

No todos los errores se manejan igual, y algunas cosas tienen que pasar siempre.

Definición
Lo que se ejecuta pase lo que pase
¿Qué es
finally?
finally
Un bloque que se ejecuta siempre, haya ocurrido una excepción o no. Sirve para código que tiene que correr de todas maneras: cerrar un archivo, liberar un recurso, avisar que terminó el intento.
try completo
try:
    v = Auto("KX12", 2018)
except ValueError as error:
    print("Error de validacion:", error)
except TypeError as error:
    print("Tipo de dato incorrecto:", error)
finally:
    print("Intento de registro terminado")
SituaciónQué se ejecuta
Todo sale bienSolo finally
Ocurre un ValueErrorEl primer except, después finally
Ocurre un TypeErrorEl segundo except, después finally
●
Varios except, uno por tipo de error

Python revisa los except en orden y ejecuta el primero que coincida con el tipo de excepción que ocurrió. Cada uno puede manejar el error de forma distinta.

Bloque 06
06 · Concepto · 12 min
La jerarquía
de excepciones

ValueError y TypeError no aparecieron de la nada: son parte de un árbol de clases.

Definición
Todas vienen de la misma raíz
Un árbol de
excepciones

Esto les va a sonar conocido: las excepciones de Python forman una jerarquía de herencia, igual que Auto y Moto heredan de Vehiculo. Casi todas las que van a usar heredan de Exception.

Exceptionla clase base de casi todos los errores
├─ ValueError valor con tipo correcto, contenido inválido -- su patente de ayer
├─ TypeError operación sobre un tipo de dato que no corresponde -- también el de Vehiculo abstracta, del bloque 2
├─ AttributeError el que vieron ayer al intentar escribir en_taller sin setter
├─ KeyError una clave que no existe en un diccionario
├─ IndexError una posición que no existe en una lista
└─ NotImplementedError el de la demo de la sesión 1 (taller_v2.py)
●
Por qué importa que sea una jerarquía

Un except Exception: atrapa cualquier error de la lista, porque todos son hijos de Exception. Es útil como red de seguridad, pero conviene ser específico primero: si atrapas todo con Exception, puedes esconder errores que en realidad querías ver.

●
El orden de los except también importa acá

Si pones except Exception: primero y except ValueError: después, el segundo nunca se va a ejecutar: el primero ya atrapó todo. El más específico siempre va primero.

Bloque 07
07 · Concepto + prompt · 20 min
Excepciones
propias del
negocio

Python no tiene una excepción para "el vehículo nunca ingresó al taller". La tienen que crear ustedes.

Definición
El momento que quedó pendiente desde la sesión 1
¿Qué es una
excepción propia?
Excepción propia
Una clase que ustedes definen, heredando de Exception, para representar un error específico de su negocio que Python no tiene predefinido.
Python sabe qué es un ValueError. No sabe qué es "intentar entregar un vehículo que nunca ingresó al taller". Eso lo definen ustedes.
excepciones.py · archivo nuevo
class VehiculoNoIngresadoError(Exception):
    def __init__(self, patente):
        super().__init__(
            f"El vehiculo {patente} no ha ingresado al taller"
        )
●
super().__init__() otra vez

Igual que ayer con Camion: se llama al constructor del padre, Exception, pasándole el mensaje ya armado con el dato específico de este error. El padre se encarga de guardar ese mensaje para cuando alguien lo imprima.

Por qué existe
El problema que resuelve, no solo la sintaxis
¿Por qué existen
las excepciones propias?

Atrapar todo con except Exception funciona, pero no dice nada sobre qué pasó específicamente: un log lleno de "Exception" a secas no ayuda a nadie a entender qué regla de negocio se violó. Una excepción con nombre propio (VehiculoNoIngresadoError) documenta la regla en el nombre mismo del error, y permite que el código que la atrapa reaccione distinto según cuál ocurrió, en vez de tratarlas todas igual.

●
En el mundo corporativo

Cualquier backend serio tiene su propio catálogo de excepciones de negocio: SaldoInsuficienteError, UsuarioNoAutorizadoError, StockAgotadoError. Cuando algo falla en producción, un sistema de monitoreo (Sentry, Datadog, o similar) agrupa los errores por su tipo exacto -- si todos fueran Exception genérica, sería imposible distinguir de un vistazo si el problema recurrente es de stock o de permisos. En Buk mismo, los servicios de dominio suelen definir errores propios para cada regla de negocio que pueden bloquear, en vez de usar excepciones genéricas de Ruby.
