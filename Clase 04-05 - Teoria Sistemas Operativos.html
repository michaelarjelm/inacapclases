Gemini CLI

Qué es, cómo funciona realmente, y cómo usarlo como herramienta de administración de servidores sin perder el control de lo que ocurre.

A

¿Qué es Gemini CLI?

Gemini CLI es un modelo de inteligencia artificial de Google que se ejecuta desde la terminal. No es un script ni una herramienta tradicional — es un modelo de lenguaje que genera texto en respuesta a lo que le escribes.

No tiene acceso directo al servidor. Solo sabe lo que tú le describes en el prompt. No puede leer archivos, ver procesos ni ejecutar comandos por sí solo — todo pasa por tu aprobación explícita.

Genera planes, comandos y explicaciones en lenguaje natural. Es útil para aprender, para recordar sintaxis y para no partir de cero. Pero lo que haces con esa información depende completamente de ti.

Analogía: Gemini es como un colega muy informado que te sugiere cómo hacer algo. Tú decides si seguir su consejo, modificarlo o ignorarlo. La responsabilidad del servidor es tuya.
Gemini CLI — interacción básica
# Gemini recibe lo que tú escribes > Eres un administrador de sistemas experto en RHEL 9. Dame el plan para actualizar el servidor. Plan primero, ejecucion despues. # Gemini genera un plan en texto Plan de actualización: 1. Verificar espacio en disco disponible 2. Revisar actualizaciones disponibles: dnf check-update 3. Actualizar el servidor: dnf upgrade -y 4. Verificar que no haya paquetes rotos 5. Reiniciar si hay actualización de kernel ¿Confirmas que ejecute el paso 1? # Tú decides si continuar o no > sí, continúa con el paso 1 Ejecutando: df -h ...
C

Modelos, tokens y cuota

Un token es la unidad básica de texto que el modelo procesa — aproximadamente una palabra. Cada vez que interactúas con Gemini consumes tokens: los del prompt que escribes más los de la respuesta que genera.

La ventana de contexto es el límite de tokens que el modelo puede "ver" en una conversación. Cuando se llena, empieza a olvidar el inicio del chat. Por eso las sesiones largas pueden volverse inconsistentes — el modelo pierde el contexto de lo que se hizo antes.

La cuota es el límite de uso del plan gratuito: requests por minuto y tokens por día. Si se agota, Gemini deja de responder hasta el siguiente ciclo. Para la clase, una cuenta por persona es suficiente.

Tip práctico: si Gemini empieza a dar respuestas inconsistentes o "olvida" lo que acordaron antes, es señal de que la ventana de contexto está llena. Lo mejor es iniciar una sesión nueva con el contexto resumido.
Token
Unidad básica de texto que el modelo procesa (~1 palabra). Cada interacción consume tokens del prompt que escribes más los de la respuesta generada. Prompts muy largos llenan el contexto más rápido.

Máximo de tokens que el modelo puede recordar en una sesión. Al llenarse, empieza a olvidar el inicio de la conversación — las respuestas se vuelven inconsistentes.

B

Buenas prácticas con Gemini

Plan primero, ejecución después. Siempre pídele el plan completo antes de que ejecute nada. Así puedes detectar errores o pasos innecesarios antes de que sucedan en el servidor.

No ejecutes lo que no entiendes. Si Gemini propone un comando que no reconoces, pídele que te lo explique antes de aprobarlo. Nunca copies y pegues a ciegas.

Valida el resultado tú mismo. Gemini puede responder "listo" cuando el comando falló silenciosamente. Siempre corre el comando de verificación correspondiente — no confíes solo en su confirmación.

Una sesión, un objetivo. El contexto de la conversación afecta las respuestas. Mezclar tareas distintas en una sola sesión puede producir respuestas inconsistentes o que confundan el estado del servidor.

Regla de oro: Gemini comete errores. Puede inventar flags que no existen, proponer comandos correctos para la distribución equivocada, o no conocer el estado real de tu servidor. Tú eres el administrador — él es solo una herramienta.

D

Anatomía de un buen prompt

Un prompt bien estructurado tiene cuatro componentes. El rol define desde qué perspectiva responde Gemini — "experto en RHEL 9" es distinto a "experto en Ubuntu".

El contexto le da información sobre la situación actual. Sin contexto, Gemini asume condiciones genéricas que pueden no aplicar a tu servidor.

La tarea describe qué debe hacer, con suficiente detalle para que no asuma cosas. Cuanto más específica, más útil la respuesta.

Las restricciones controlan cómo lo hace: plan primero, un paso a la vez, esperar aprobación. Sin ellas, Gemini puede ejecutar todo de golpe sin darte tiempo de revisar.

Regla: un prompt que no tiene rol, contexto, tarea y restricciones es un prompt incompleto — y una respuesta incompleta o incorrecta es el resultado más probable.

Permisos Unix: rwx y octal

Cada archivo tiene 9 bits de permisos divididos en 3 grupos: propietario, grupo, otros. Cada grupo puede tener hasta 3 permisos.

LetraNombreValorPermite
rread4Leer el archivo
wwrite2Modificar el archivo
xexecute1Ejecutar el archivo
-ninguno0Sin acceso

Los valores se suman para obtener el número octal de cada grupo. Ejemplo con chmod 750:

GrupoPermisosCálculoOctal
Propietariorwx4+2+17
Grupor-x4+0+15
Otros---0+0+00
Conexión con la práctica: chmod 750 /usr/local/bin/gemini — root controla todo, wheel puede ejecutar, el resto no puede ni verlo.

Desglose de permisos — ls -la /usr/local/bin/gemini

- rwx r-x ---
Propietario (root) r+w+x = 4+2+1 = 7
Lee, escribe, ejecuta
Grupo (wheel) r+x = 4+0+1 = 5
Lee y ejecuta, no escribe
Otros --- = 0+0+0 = 0
Sin ningún acceso
# Octal resultante
chmod 750 /usr/local/bin/gemini

chmod y chown: asignar permisos

Saber calcular octal es la teoría. chmod aplica los permisos al archivo y chown define quién es el dueño y el grupo. El patrón chown root:GRUPO + chmod 750 es la técnica para restringir cualquier herramienta a un grupo específico.

ComandoPropietarioGrupoOtrosCaso de uso
chmod 750 archivorwxr-x---Herramienta solo para el grupo
chmod 644 archivorw-r--r--Archivo de configuración público
chmod 600 archivorw-------Clave privada SSH (.pem)

El mismo patrón, aplicado a las herramientas de la evaluación:

HerramientaGrupo autorizadoRuta del binario
nano administrativos (wheel via sudo) $(which nano) → /usr/bin/nano
cowsay medicos $(which cowsay) → /usr/bin/cowsay

/etc/passwd y shadow

Cada línea de /etc/passwd describe un usuario con 7 campos separados por ":". La contraseña real nunca está aquí.

#CampoEjemploQué es
1Usuariodocente01Nombre de login
2Contraseñax"x" significa que está en /etc/shadow
3UID1001Identificador numérico del usuario
4GID1002Grupo primario — el número, no el nombre

Mínimo privilegio

Cada usuario solo debe tener los permisos mínimos necesarios para su función. Si una cuenta es comprometida, el atacante solo llega hasta donde esa cuenta puede ir.

Usuario / RolsudoGeminiSSHAlcance
root Sí Sí No directo Control total del sistema
ec2-user (wheel) Sí Sí Sí Administrador via sudo
docente01 (docentes) No No Sí Solo su directorio home
alumno01 (alumnos) No No Sí Solo su directorio home
Principio de diseño: parte sin acceso y otorga solo lo necesario. Es más fácil abrir permisos que cerrar los que ya están abiertos.

Jerarquía de privilegio en el servidor

root
Control total del sistema. UID 0. Nunca se usa directamente — se accede via sudo.
↑ sudo ↑
wheel
Puede ejecutar sudo. Accede a Gemini. Solo ec2-user pertenece a este grupo.
↑ grupos ↑
docentes
Acceso SSH al servidor. Sin sudo. Sin Gemini. Solo puede operar en su home.
alumnos
Acceso SSH limitado. Sin sudo. Sin Gemini. Mínimo privilegio aplicado.

sudo y su

Dos comandos para ejecutar acciones con los privilegios de otro usuario. sudo es el camino correcto en RHEL 9 — ejecuta un solo comando como root y deja registro. su cambia de usuario completamente.

ComandoQué haceContraseña que pide
sudo comando Ejecuta UN comando como root. Requiere que tu usuario esté en el grupo wheel La tuya propia
sudo -i Abre un shell interactivo como root. Usar solo cuando es estrictamente necesario La tuya propia
su usuario Cambia completamente al usuario indicado y abre su shell La del usuario destino
su -c "cmd" usuario Ejecuta UN comando como el usuario indicado sin cambiar de sesión La del usuario destino
Por qué sudo y no su root: con sudo, cada acción queda registrada en /var/log/secure con el usuario real que la ejecutó. Con su root, el sistema solo ve "root" — sin trazabilidad.
bash — sudo vs su en la práctica
# sudo: funciona porque ec2-user está en wheel [ec2-user@srv ~]$ groups ec2-user ec2-user wheel [ec2-user@srv ~]$ sudo groupadd docentes (sin error = comando ejecutado como root) # su -c: probar si docente01 puede usar sudo [ec2-user@srv ~]$ su -c "sudo whoami" docente01 Password: # contrasena de docente01 docente01 is not in the sudoers file. # docente01 no esta en wheel → no puede usar sudo # Esto es exactamente la validacion del Prompt 2 # El registro queda en /var/log/secure [ec2-user@srv ~]$ sudo tail -3 /var/log/secure sshd: Accepted publickey for ec2-user sudo: ec2-user : COMMAND=/usr/sbin/groupadd docentes sudo: docente01 : user NOT in sudoers

Daemons y systemd

Un daemon es un proceso que corre en segundo plano, sin intervención del usuario, esperando eventos o peticiones. SSH, el firewall y el scheduler de tareas son todos daemons.

systemd es el proceso PID 1 en RHEL 9 — el padre de todos los procesos. Reemplazó a init, SysVinit y Upstart porque hace el arranque en paralelo (más rápido), permite declarar dependencias entre servicios sin escribir lógica de espera, y centraliza todos los logs en journald — accesibles con journalctl en vez de buscar en archivos dispersos.

Analogía: systemd es el administrador del servidor. Sabe qué servicios deben correr, en qué orden, y qué hacer si fallan.
systemctl — inspeccionar servicios
# PID 1 siempre es systemd [ec2-user@srv ~]$ ps -p 1 PID TTY CMD 1 ? /usr/lib/systemd/systemd # Ver estado de un servicio [ec2-user@srv ~]$ systemctl status sshd ● sshd.service - OpenSSH server daemon Loaded: loaded (/usr/lib/systemd/system/sshd.service) Active: active (running) since Sun 2026-05-03 Main PID: 892 (sshd) Tasks: 1 # Ver todos los servicios activos [ec2-user@srv ~]$ systemctl list-units --type=service \ --state=running UNIT ACTIVE DESCRIPTION crond.service active Command Scheduler firewalld.service active Firewall sshd.service active OpenSSH server

Ciclo de vida de un servicio

Instalar un paquete no es suficiente — hay que controlar cuándo corre y si sobrevive al reinicio. systemctl es el comando que gestiona ese ciclo.

ComandoEfecto inmediatoPersiste al reinicio
systemctl start sshdArranca ahoraNo
systemctl stop sshdDetiene ahoraNo
systemctl enable sshdNoSí — arranca en el boot
systemctl disable sshdNoSí — no arranca en el boot
systemctl mask sshdBloquea — ni manual ni bootSí
Error común: systemctl stop sin disable — el servicio vuelve a correr en el próximo reinicio. Para apagarlo del todo: stop + disable.
bash — cowsay + ciclo de un servicio real
# Instalar cowsay (herramienta, no daemon) [ec2-user@srv ~]$ sudo dnf install cowsay -y Complete! [ec2-user@srv ~]$ cowsay "Aprende systemctl!" ____________________ < Aprende systemctl! > -------------------- \ ^__^ \ (oo)\_______ (__)\ )\/\ ||----w | || || # sshd es un daemon real — veamos su ciclo [ec2-user@srv ~]$ systemctl is-active sshd active [ec2-user@srv ~]$ systemctl is-enabled sshd enabled # Detener sin deshabilitar = vuelve al reinicio [ec2-user@srv ~]$ sudo systemctl stop sshd [ec2-user@srv ~]$ systemctl is-active sshd inactive [ec2-user@srv ~]$ systemctl is-enabled sshd enabled # aun arranque en el proximo boot # Correcto: stop + disable [ec2-user@srv ~]$ sudo systemctl disable --now sshd

Unidades .service vs .socket

  • systemd gestiona diferentes tipos de unidades: service, socket, timer, mount, target, entre otras.
  • .service: proceso que corre continuamente en segundo plano.
  • .socket: escucha conexiones y arranca el .service correspondiente solo cuando llega una conexión. Ahorra memoria cuando el servicio se usa poco.
  • cockpit.socket es un ejemplo real: Cockpit solo levanta cuando alguien abre el puerto 9090 en el navegador.
Por eso deshabilitamos cockpit.socket y no cockpit.service en la práctica — la unidad activa era el socket, no el servicio.
bash — .service vs .socket en acción
# .service: proceso siempre corriendo en memoria [ec2-user@srv ~]$ systemctl status sshd.service ● sshd.service - OpenSSH server daemon Active: active (running) Main PID: 892 (sshd) # sshd siempre ocupa RAM, escucha puerto 22 sin parar # .socket: systemd escucha, el servicio arranca solo si alguien conecta [ec2-user@srv ~]$ systemctl status cockpit.socket ● cockpit.socket - Cockpit Web Service Socket Active: active (listening) Listen: 0.0.0.0:9090 # puerto 9090 abierto, pero cockpit.service NO corre — sin consumo de RAM # Por eso deshabilitamos el .socket y no el .service [ec2-user@srv ~]$ sudo systemctl disable --now cockpit.socket Removed .../sockets.target.wants/cockpit.socket # Verificar que ya no escucha en 9090 [ec2-user@srv ~]$ sudo ss -tlnp | grep 9090 (sin resultado)

Superficie de ataque

La superficie de ataque es la suma de todo lo que un atacante puede intentar explotar en un sistema: puertos abiertos, servicios corriendo, usuarios con acceso, software instalado.

Cada servicio activo es un punto de entrada potencial. Tiene un proceso escuchando en un puerto, código que puede tener vulnerabilidades, y credenciales que alguien podría intentar robar. Si no usas ese servicio, deshabilitarlo elimina ese vector de ataque sin ningún costo operativo.

Reducir la superficie de ataque es una de las medidas de hardening más efectivas porque no requiere configuración compleja — solo apagar lo que no se necesita.

Regla de oro: si no sabes para qué sirve un servicio corriendo en tu servidor, es razón suficiente para investigarlo. Si no lo necesitas, apágalo.

en Linux

Cómo el kernel filtra paquetes, qué son las zonas de firewalld, los puertos bien conocidos, y por qué en AWS hay dos capas de firewall.

13

netfilter y firewalld

netfilter es el framework dentro del kernel Linux que intercepta y filtra cada paquete de red que entra o sale del servidor. Es el motor real del firewall — todo lo demás es una interfaz para configurarlo.

nftables es la herramienta moderna para escribir reglas en netfilter, reemplazando al antiguo iptables. Y firewalld es el demonio de RHEL 9 que gestiona nftables con una abstracción más amigable basada en zonas y servicios.

En la práctica tú escribes firewall-cmd, firewalld lo traduce a reglas nftables, y el kernel las aplica. Cada capa simplifica la anterior.

Capas de abstracción: firewall-cmd → firewalld → nftables → netfilter (kernel).

Flujo de un paquete entrante

Internet — paquete llega a la interfaz de red
↓
AWS Security Group — primer filtro (capa de nube)
↓ (si el SG lo permite)
netfilter (kernel) — firewalld aplica reglas nftables
↓ (si la zona lo permite)
Proceso destino — sshd, httpd, etc.
Un paquete debe pasar ambas capas para llegar al proceso.
14

Zonas de firewalld

Una zona es un nivel de confianza que firewalld asigna a una interfaz de red. Según la zona, se permiten o bloquean distintos servicios y puertos. En AWS, la interfaz eth0 queda en la zona public por defecto — la más restrictiva para redes desconocidas.

Las zonas no filtran por IP de origen, sino que definen una política general para todo el tráfico que entra por esa interfaz. Si necesitas dar más confianza a un rango de IPs específico, puedes asignarlas a una zona distinta con --add-source.

La tabla de la derecha muestra las zonas de menor a mayor confianza. En un servidor en internet, lo correcto es quedarse en public y permitir solo los servicios estrictamente necesarios.

Puertos bien conocidos

Los puertos van del 0 al 65535 y se dividen en tres rangos. Los well-known (0-1023) están asignados por la IANA a servicios estándar como SSH (22), HTTP (80) o HTTPS (443). Solo root puede abrir un proceso que escuche en ellos.

Los registered (1024-49151) también los asigna la IANA, pero a aplicaciones más específicas como MariaDB (3306) o Cockpit (9090). Cualquier usuario puede escuchar en ellos sin privilegios especiales.

Los ephemeral (49152-65535) los asigna el kernel dinámicamente cada vez que tu PC inicia una conexión saliente — son los puertos del cliente, no del servidor.

Por qué importa: abrir el puerto 80 en el firewall solo tiene efecto si hay un proceso escuchando ahí. Si no hay proceso, el paquete llega al servidor y muere sin respuesta.

Dos capas de firewall

En AWS, el tráfico pasa por dos firewalls independientes antes de llegar al proceso. El Security Group opera a nivel de red virtual (VPC), fuera de la instancia — filtra por IP, puerto y protocolo antes de que el paquete llegue al sistema operativo.

El segundo filtro es firewalld, que corre dentro del sistema operativo a nivel de kernel. Es completamente independiente del Security Group — ninguno conoce al otro.

Un puerto debe estar abierto en ambos para que el tráfico llegue al proceso. Si uno lo bloquea, el paquete no pasa sin importar cómo esté configurado el otro.

Ejemplo real: al levantar Nginx en el puerto 8080 con Podman, tuvimos que abrirlo en firewalld y en el Security Group de la consola AWS. Solo uno no alcanza.

Hardening de SSH

Por qué las contraseñas son inseguras en SSH, cómo funciona la criptografía asimétrica, y qué directivas de sshd_config reducen el riesgo real.

19

Por qué deshabilitar contraseñas

Un servidor con el puerto 22 abierto en internet recibe intentos de login SSH a los pocos minutos de estar online. Bots automatizados escanean rangos de IPs continuamente buscando servidores con contraseñas débiles.

Los dos ataques más comunes son la fuerza bruta — probar millones de combinaciones usuario/contraseña hasta acertar — y el credential stuffing, que usa credenciales filtradas de otras brechas asumiendo que la gente reutiliza contraseñas.

Con PasswordAuthentication no el servidor rechaza directamente cualquier intento de login con contraseña y solo acepta llaves criptográficas, haciendo ambos ataques imposibles.

Dato real: un servidor AWS con puerto 22 abierto recibe entre 1.000 y 10.000 intentos de login por día. Con Fail2ban instalado se pueden ver en tiempo real.

Criptografía asimétrica

La criptografía asimétrica genera dos llaves matemáticamente relacionadas: una pública, que se puede compartir libremente, y una privada, que nunca sale de tu PC. Lo que se cifra con una solo lo puede descifrar la otra.

En SSH, el servidor guarda tu llave pública en ~/.ssh/authorized_keys. Al conectarte, el servidor te envía un desafío cifrado con esa llave. Solo quien tiene la llave privada puede resolverlo — sin necesidad de enviar ningún secreto por la red.

Incluso si alguien intercepta toda la comunicación, no puede impersonarte sin la llave privada. Y no hay contraseña que adivinar: una llave de 3072 bits tardaría más que la edad del universo en crackearse por fuerza bruta.

Ventaja clave: la autenticación ocurre sin transmitir ningún secreto. La llave privada nunca viaja por la red.

Directivas de sshd_config

/etc/ssh/sshd_config es el archivo de configuración del servidor SSH. Cada directiva controla un aspecto del comportamiento — quién puede conectarse, cómo se autentica, cuánto tiempo puede estar inactiva una sesión.

Los cambios no tienen efecto hasta hacer systemctl restart sshd. Si hay un error de sintaxis, sshd no reinicia y pierdes el acceso. Por eso siempre se valida primero con sshd -T, que revisa la configuración completa sin tocar el servicio.

AllowUsers es una whitelist explícita — solo los usuarios listados pueden conectarse por SSH, sin importar si tienen contraseña válida o llave registrada. Es más seguro que depender solo de los grupos.

Protocolo de seguridad: mantén siempre una sesión SSH abierta mientras editas sshd_config. Si algo falla, puedes corregirlo sin perder el acceso al servidor.
DirectivaValor seguroQué hace
PermitRootLogin no Impide login directo como root — el atacante debe saber también el usuario.
PasswordAuthentication no Solo acepta llaves criptográficas. Elimina la fuerza bruta de contraseñas.
AllowUsers ec2-user Whitelist de usuarios que pueden conectarse por SSH. Cualquier otro es rechazado.
MaxAuthTries 3 Cierra la conexión después de 3 intentos fallidos. Dificulta la fuerza bruta.
ClientAliveInterval 300 Cierra sesiones inactivas después de 5 minutos. Reduce ventana de ataque.
Protocol 2 Solo SSH v2 — SSHv1 tiene vulnerabilidades conocidas.

El riesgo de bloquearse

Un error en sshd_config puede dejarte sin acceso al servidor de dos formas distintas. Si hay un error de sintaxis y reinicias sshd, el daemon no levanta — el servicio queda caído y nadie puede conectarse por SSH.

El segundo caso es más silencioso: si escribes mal tu usuario en AllowUsers, sshd reinicia correctamente pero te rechaza al intentar conectarte. El servicio funciona, pero tú quedas afuera.

En AWS esto es recuperable via Session Manager desde la consola EC2, pero en un servidor físico o en otro proveedor puede significar perder el acceso definitivamente. El procedimiento correcto es validar con sshd -T, reiniciar, y verificar desde una segunda terminal antes de cerrar la sesión actual.

Lección operacional: la diferencia entre un sysadmin junior y uno senior no es saber más comandos — es saber validar antes de aplicar.

Apache y Virtual Hosts

Un Virtual Host permite que un solo servidor Apache sirva múltiples sitios web en el mismo puerto. Apache distingue a cuál responder usando el header Host: que el navegador envía en cada petición — ese header contiene el dominio que escribió el usuario.

Cada sitio tiene su propio bloque de configuración en /etc/httpd/conf.d/. Las tres directivas esenciales son ServerName (a qué dominio responde), DocumentRoot (dónde están los archivos) y ErrorLog (dónde guardar los errores).

El sitio por defecto, sin Virtual Host configurado, sirve desde /var/www/html/ — el index.html que creamos en la práctica al instalar Apache.

Validar siempre antes de recargar: apachectl configtest revisa la sintaxis de todos los archivos de configuración sin tocar el servicio.
/etc/httpd/conf.d/sitio.conf — Virtual Host
# Un servidor, dos sitios en el mismo puerto 80 <VirtualHost *:80> ServerName www.inacap-sitio1.cl DocumentRoot /var/www/sitio1 ErrorLog /var/log/httpd/sitio1-error.log </VirtualHost> <VirtualHost *:80> ServerName www.inacap-sitio2.cl DocumentRoot /var/www/sitio2 ErrorLog /var/log/httpd/sitio2-error.log </VirtualHost> # Apache lee el header "Host:" del navegador: # Host: www.inacap-sitio1.cl → sirve /var/www/sitio1 # Host: www.inacap-sitio2.cl → sirve /var/www/sitio2 # Verificar sintaxis antes de recargar [root@srv ~]# apachectl configtest Syntax OK

Separación de capas

Un servidor web bien diseñado separa tres responsabilidades: presentación (HTML/CSS que ve el usuario), lógica (PHP o Python que procesa los datos) y datos (la base de datos que los almacena). Cada capa hace una sola cosa.

El navegador solo habla con Apache en el puerto 80 o 443. Apache delega los archivos PHP al intérprete, que consulta MariaDB internamente en 127.0.0.1:3306. La base de datos nunca está expuesta directamente a internet.

En producción, cada capa puede vivir en servidores distintos para escalar de forma independiente. Pero incluso en un solo servidor, el puerto 3306 debe estar cerrado en el firewall — la contraseña de la base de datos es una defensa, la red es otra.

Principio de diseño: la base de datos no debería ser accesible desde internet aunque tenga contraseña. Tener ambas defensas es mejor que confiar en una sola.

HTTP vs HTTPS

HTTP (puerto 80) transmite todo en texto plano. Cualquier dispositivo entre tu PC y el servidor — routers, ISPs, redes WiFi públicas — puede leer exactamente lo que envías y recibes, incluyendo contraseñas.

HTTPS (puerto 443) cifra la comunicación con TLS usando el mismo principio de criptografía asimétrica que vimos en SSH: las partes negocian una clave de sesión sin transmitirla. Incluso si alguien intercepta el tráfico, solo ve datos cifrados ilegibles.

El certificado TLS también autentica el servidor — el navegador verifica que está hablando con el servidor correcto y no con un impostor que interceptó la conexión. Por eso muestra el candado verde.
